## 1. 摘要

bot 项目已经过剩。再做一个"具名 bot + 群聊 + @"，无论做得多完整，都会落进同一个货架。

Lodge 的判断是：**这个品类缺的不是更多 bot，而是"小队"这件事本身**——一场有议程、有席位、有交付、有验收的讨论。

但"小队"只是骨架。用户为两件事付钱：**这次交付有人替他干完并验收；换人、换引擎或一个月后，这间房还能接上。** 前者是省时省力，后者是留痕与可交接——省时省力是结果，不是唯一理由。所以本文的第二条主线是苹果式设计：极简、表里如一、人的感受优先、端到端一体；展开成默认即最佳、一次一个决定、结果优先、一切可撤销。功能再多，只要需要用户先理解你的机制，或者界面上写着机制里没有的事，就是失败的。

结论：

- **一等公民是群（Room），不是 bot**：bot 可换、引擎可换、模型可换，群不能
- **3 个真创新**：房间即仓库（已落）、游标可见（已落）、独立验收（多验收/盲审已落；跨厂商依赖第二引擎）
- **2 个组合创新**：发言权预算（成本闸门已落，发言配额未强制）、可分叉会议（可 fork 房间，并排会议未做）
- **1 个执行优势**：验收是命令（已落）
- **4 条产品核心 + 8 条苹果式原则**，每条都落到一个具体的删除动作或验收约束
- **28 条设计理念直接照搬**（17 条机制 + 11 条交互）；其中 Assignment 运行时以 OpenMausBot OSS 为基座复用（Apache-2.0）；当前仍用基座线程/回合承载，尚未切到上游 Assignment 生命周期
- **6 件事必须重写**：产品面、会话模型、群策略、API runtime、记忆层、上游多余能力
- **技术选型已定**：OpenMausBot OSS 基座 + 它的 drivers/ACP 引擎层 + Electron 外壳，Mac arm64 先行；不引入第三方编排框架（§10.0）

一个必须正视的现实：**Grok Bot、Dots、Duet、Muse、Cue 全是"常驻个人 agent"**，而且 Grok Bot 有「Chief of Staff + 专家 Bot + 共享群线程」，Cue 有「多 agent 共享群聊 + 共享目标 + 交接」。所以"多个 agent 在一个群里协作"已经不是差异点，是入场券。

Lodge 唯一的护城河是：**跑在你自己的仓库上、用你已付费的真实 CLI、靠证据验收、由不同厂商交叉审查**。这四件事，云端个人 agent 都做不了——它们的机器不是你的，它们的模型是固定的。

## 2. 产品哲学：像 iPhone 4 一样，表里如一地做减法

### 2.1 一句话

科技与艺术交汇：**极简、表里合一、优先人的完整体验；技术服务感受，而不是堆砌参数。**

乔布斯对设计的定义是本文的检验尺：**设计不只是外观，设计是它整体怎么工作。** 好看只是一部分，好用、舒服、浑然一体才是目标。

### 2.2 四条核心

| 核心 | 原意 | 在 Lodge 里怎么落地 |
|---|---|---|
| **极简，去掉多余** | 方正、干净、造型克制；能整合的就整合（边框直接当天线），少即是多 | 一屏、一条进度带、四种时间线元素（发言、任务卡、证据、结论卡）；没有仪表盘、没有模式选择器、没有成员管理页。新功能先问一句：能不能并进已有卡片 |
| **表里如一，材质诚实** | 材料本身就是美感，不靠喷漆、装饰伪装；内部结构服务外形，不是外壳套一个随便的内部 | 界面上的每句话都必须对应真实机制：说「已写入 evidence/」就真有文件，说「本地 commit 一次」就真有 commit，说「跨厂商」就真是两个厂商。演示/样例数据必须标注；交付型阶段没有 Verifier PASS 就不能通过（§9.3） |
| **优先人的感官体验，技术为感受服务** | 视网膜屏的逻辑：人眼在正常距离分辨不出像素就够了，不盲目堆分辨率；追求自然、像印刷纸张一样的观感；易用优先，功能藏在简洁交互里 | 默认不让人选模型、参数、并发；30 秒开队、最多 3 个问题、每个带推荐答案；失败说人话；证据先跑好，人只做「接受 / 不要」 |
| **端到端完整掌控，软硬件一体** | 苹果自己掌控硬件、系统、交互全链路，深度配合，保证流畅统一，而不是分开拼凑 | 房间即仓库：目标、席位、worktree、验收命令、证据、结论在同一条链上；不是给 CLI 套一个聊天壳。引擎可换，但房间、证据、验收规则不能换 |

### 2.3 四条核心展开成八条可执行原则

| # | 原则 | 具体做法 | 反例（不要） |
|---|---|---|---|
| 1 | **默认即最佳** | 打开就是一个建队入口；规划师先给分工与 BRIEF 草稿 | 首次启动弹配置向导 |
| 2 | **一次一个决定** | 任何时刻界面上最多一个待你回答的问题，且已带推荐答案 | 一次甩出 6 个选项让你配 |
| 3 | **只说目标，不管过程** | 用户永远不需要知道 roundtable / lead-first / worktree / 水位线 | 让用户选"讨论模式" |
| 4 | **渐进披露** | 引擎、工位、预算、发言权全在"高级"里，默认不出现 | 主界面放一排开关 |
| 5 | **结果优先** | 首屏看到 diff、证据、一句结论，不是滚动聊天 | 把界面做成聊天记录 |
| 6 | **一切可撤销** | 每步可回退；停止永远可用；不产生不可逆操作 | 自动 push、自动合并 |
| 7 | **安静** | 不主动弹窗；进度用一条细带；只有需要你时才亮（Muse 的 proactivity 可调） | 每完成一步就通知 |
| 8 | **失败说人话** | "Codex 没能启动，可能还没登录" | `exit 127` + 堆栈 |

### 2.4 三个可量化的承诺

| 承诺 | 数字 | 怎么做到 |
|---|---|---|
| 30 秒开队 | 打开到开始干活 ≤ 30 秒，问题 ≤ 3 个 | 目标对齐只问真正要人拍板的分叉，每个带推荐答案 |
| 一屏看完 | 不需要切 tab、不需要展开任何面板 | 进度压成一条带，任务板默认折叠 |
| 一次点击验收 | 成果就在眼前，只有"接受 / 不要"两个选择 | 证据先跑好，人只做判断 |

三个承诺合起来是一句话：**用户只做三件事——说目标、答最多三个问题、验收。**

### 2.5 由此砍掉的东西

- **砍掉模式选择器**：模式由系统按目标判断
- **砍掉配置向导**：所有参数有默认值，想改去"高级"
- **砍掉仪表盘首页**：打开就是当前目标，没有"概览"
- **砍掉成员管理页**：席位固定为规划师/执行者/验收员，人只确认开工卡；建后增删/改角色属于封口扩展
- **砍掉会话列表**：一个目标一个房间，不是一堆聊天

### 2.6 一句话检验

每个新功能上线前问两个问题：

1. **"用户需要先学一个新概念吗？"** 需要，就说明设计还没做完。
2. **"界面上的承诺，背后有真实机制吗？"** 没有，就先别写这句话——这是"表里如一"的底线，也是验收清单的常驻项。

第一条检验的是**交互概念**，不是内部本体：用户不需要先理解“房间”才能用目标岛；但每次交付都必须让他看见房间留下的证据、结论与一次 commit。藏住机制可以，藏住机制留下的凭证不行。

## 3. 先说清楚不是什么

大多数同类项目的默认形状是「花名册」：左栏一排 bot，点进去聊天，群里 @ 一下。

| 维度 | 机器人集合（大多数） | Lodge（工作小队） |
|---|---|---|
| **核心对象** | 一个一个的 bot | **一个群（Room）** |
| 首屏 | 最近会话列表 | 当前目标 + 一条进度带 |
| 成员 | 人设、头像、语气 | 工位：职责、引擎、写入范围（默认折叠） |
| 群 | 方便 @ 的聊天室 | 有议程、有阶段、有交付的房间 |
| 发言 | 谁被 @ 谁说 | 有席位、有发言配额、有已读游标 |
| 完成 | "我做完了" | 证据 + 验收命令 + diff |
| 结束 | 聊天记录 | `CONCLUSION.md`（运行时结论）+ `decisions.md`（人）+ 一次 commit |

**明确不做**：

- 不做通用 Memory 系统——CLI 自己有记忆，我们只需要房间级的 `BRIEF.md`
- 不做 Connector / Browser / Computer use / IM 接入——那是 Dots、Duet、Muse 的战场
- 不做常驻云电脑、不做钱包与支付——那是 Grok Bot、Cue 的形态
- 不做"人格扮演"——成员是工位，不是角色
- 不做无边界自由聊天——必须有发言权预算、空转守卫、成本上限
- 不做移动端优先——这是桌面工作台
- 不做部门 / 组织层级——需求用「编制模板 + 工作区」解决（§8.7）

## 4. 六家的取舍

参考不是模仿。下面每一家都解决了一个我们没有的问题，也暴露了一个我们不该踩的坑。

### 4.1 CrewAI：把"角色 + 预期产出"变成第一类

**真实形态**：代码框架。`Agent(role, goal, backstory, tools)`、`Task(description, expected_output)`、`Crew(agents, tasks, process=sequential|hierarchical)`。层次流程里由一个 manager agent 派活并复核。

**最值得学的一条**：`Task.expected_output` 是必填的——每个任务**出生时就带着"交付物长什么样"**。这和 §9 的"先对齐 done"是同一个洞察的两端，它把它写进了类型系统。

**顺带抄的两条**：
- **hierarchical process**：队长派活 + 复核，正是我们的 Assignment 模型
- **task guardrails**：每任务可挂校验函数，正是我们的 `acceptance_cmd`

**不学**：让用户写 YAML / 代码来编排流程。

### 4.2 Grok Bot：最接近我们的形态，也最值得警惕

**真实形态**（2026-08 beta）：一批持久化的**具名数字同事**，每个有自己的云电脑（浏览器 / 文件 / 终端），关掉笔记本还在干。Bot 像人一样登录应用和网站，所以没有 API 的老系统也能操作。核心对象是 Bots / Chats / Prompts / Tools / Artifacts / Routines（看一遍你干活就存成可复用流程）。一个 **Chief of Staff** Bot 管理一群专家 Bot（研究、收件箱、报销、招聘、差旅、调试），它们可以互相私聊，也可以在**共享群线程**里协作。据说两个月做到 80 万周付费用户。

**最值得学的四条**：
- **Chief of Staff 是产品角色，不是框架概念**：用户看到的是"我有一个主管"，不是一个编排器。我们的队长应该同理
- **Bot 之间可以私聊**：不是所有协作都要在群里。我们照此允许成员之间直连，只在必要时把结论带进房间
- **Routines 来自"跟着你看一遍"**：不要求用户写自动化，而是从一次真实操作里录下来。这对应我们的"这一轮的做法存成模板"
- **产品感优先**：它的技术都是旧的（云电脑 Manus 早就有），赢在包装

**必须避开的三个坑**（已知缺陷，正好是我们的机会）：
- **所有 Bot 共用一台云电脑**，隔离只到用户级，官方文档直言"不要把不同 Bot 当安全边界"。我们的答案是**一人一个 git worktree**
- **不能选模型**，后端路由不透明。我们的答案是**引擎可见可选，且谁说的标在消息上**
- **没有企业级控制层**：没有范围权限、升级规则、审计。我们的答案是审批桥 + 事件流

**不学**：常驻云电脑、用登录态操作他人系统。

### 4.3 OpenAI Dots：常驻、主动、可审批

**真实形态**：DevDay 2026 发布。每个 Dot 有自己的云电脑和浏览器，可接 4000+ 应用，持续朝目标工作，后台只读扫描你的应用并主动提供信息。敏感操作要审批，有 Activity View。

**最值得学的三条**：
- **主动研究默认只读**：只扫描、不改动。我们照此设计讨论阶段——全员只读同一份 base
- **敏感动作审批**：改密码、装软件要点头
- **Activity View**：能看见它干了什么。我们对应证据时间线

**不学**：常驻云电脑、应用海、主动推送。我们的"常驻感"用本地方式实现：打开应用时后台只读看一眼 `git status`、失败测试、未读消息，只在顶栏留一个安静的点。

### 4.4 Claude Duet：简报式汇报，而不是聊天式追问

**真实形态**：2026-10 研究预览的独立 agent 应用（iOS / Android / Web），主动监控连接的应用，每天一份简报，后台持续工作。发消息、付款、签文件、删除前一律要批准。

**最值得学的两条**：
- **它找你说，而不是你找它**：产出以"简报"到达——做了什么、哪里需要你拍板。我们对应每轮一张**结论卡**
- **审批前置**：不是做完再问，而是动手前问

**不学**：6000+ 连接器、支付、云 VM。

### 4.5 Manus Cue：一次确认完成整件事

**真实形态**：Manus 2.0 同期发布。每个 agent 有自己的邮箱、电话、钱包和云电脑；扫二维码就能下单；**支持多个 agent 在同一群聊里共享目标、互相交接**。

**最值得学的两条**：
- **一次确认完成整件事**：用户只在最后点一次"确认支付"。我们对应一键验收
- **交互密度低**：一屏内完成，不跨页

**必须正视**：群聊协作 Cue 已经有了。所以它只是入场券。

**不学**：生活助理、钱包、电话。

### 4.6 Meta Muse：把守门做成一个独立角色

**真实形态**：2026-09 在 iOS / Android / Web / WhatsApp 上线。跑在独立的 "Muse Secure VM" 里，网络与连接器动作由一个单独的 **Sentinel** agent 把关，敏感操作要用户批准。有浏览器、文件、终端，能后台持续跑，有审计记录。11 月加了 Spaces——**一句话生成一个会自更新的迷你应用**。

**最值得学的三条**：
- **守门是一个独立 agent，不是主 agent 的一段 prompt**：这比"提示模型要谨慎"可靠得多。我们的审批桥应该按这个思路做——独立判定，不与被审对象共享上下文
- **主动程度可调**：用户可以调它多主动。我们的"安静"原则应该给一个连续档位，而不是二值开关
- **Spaces 的启发**：用户真正想要的是"一个能持续更新的小工具"，不是一段聊天记录。我们的房间最终态也许该长得像一个持续更新的交付面板

**不学**：云 VM、连接器、数据默认用于训练。

### 4.8 六家的取舍，落成产品动作

原则：**每家只借一件，落到界面上一个已有位置；不新增页面。** 六家合起来不是六个功能，而是一条完整链路：

```
开队（CrewAI）→ 房间与队长（Grok）→ 阶段只读（Dots）→ 结论卡（Duet）→ 一键验收（Cue）→ 交付单（Muse）
```

| 来源 | 借的那条 | 产品里的具体样子（用户看到什么） | 首版 |
|---|---|---|---|
| **CrewAI** | 交付物先于执行 | 新房间先写“做完的样子”（done），再出现阶段；每个阶段卡写清“产出什么 + 怎么算过”，不是先选人、选引擎 | 做 |
| **Grok Bot** | 队长是产品角色；成员可直连 | 对外席位叫 **规划师 / 执行者 / 验收员**（内部仍是 planner / executor / verifier）；成员私下对过的事，主时间线只留一条“谁和谁对过 · 结论是什么”，不出现私聊全文 | 队名做；直连 v1.1 |
| **Dots** | 主动研究默认只读；活动可查 | 第一个阶段标 **只读讨论**，全员读同一份 base、不改仓库；证据按时间线排，不另开 Activity 页 | 做 |
| **Duet** | 简报式汇报，不是聊天 | 每个阶段结束一张结论卡：**做了什么 / 证据 / 下一步要你决定什么**；没有下一步就写“无需你操作” | 做 |
| **Cue** | 一次确认完成整件事 | 验收只有一个主动作 **接受这一阶段**；不跨页、不二次确认、不问“确定吗” | 已有 |
| **Muse** | 独立守门；终态是持续更新的交付面板 | Verifier 是独立席位，审批桥不与被审对象共享上下文；完成态是 **交付单**（目标、阶段、命令、改动文件、commit），不是聊天记录 | 交付单已落；独立模型守门/主动档位 v1.1 |

**2026-11-12 补齐**：每阶段一张简报式结论卡；用户说“不对，重来”后记录意见、作废旧 PASS、重审目标并返工当前阶段；圆桌讨论阶段只读；阶段开始时写一条规划师派活留痕；最后阶段显示整房交付摘要，确认后才完成。私聊、主动档位、跟做生成模板仍后置。

**为什么后置的三条不是浪费**

- **私聊直连（Grok）**：架构保留“只回结论”的格式，但首版不开放入口。私聊不可审计时，用户无法判断房间里那句话从哪来；等审计与摘要都可靠再开。
- **主动档位（Muse）**：没有真实的后台检查，就没有可调的“主动”。首版固定最安静的档位，不做假开关。
- **跟做生成模板（Grok）**：模板要从一次真实完成的轮次里录，不是让模型编一份。等真实引擎跑通后再加“把这次存成模板”。

**明确不借的**：云电脑、连接器海、支付/电话/邮箱、把数据用于训练、用登录态操作他人系统。它们不是设计取舍，是产品边界。

### 4.9 竞争定位：先卖证据与验收（2026-11-12）

**护城河排序**：本地仓库 + 真实 CLI + 证据验收是当下就能兑现的卖点；跨厂商是 M4 的增强项，不是入场券。同引擎时必须标“独立性降级”，不拿未实现的能力当主卖点。

**一句话**：云端 agent 告诉你它做完了，Lodge 证明它做完了。

**战场**：不和 Grok Bot 比“同事感 / 常驻 / 生活助理”；比交付审计：一人一 worktree、退出码 + diff + commit、关掉页面后 `git status` 仍然说明发生过什么。

**传播**：不做模板市场；做“可 clone 的房间样本”。官方只维护 3–5 个真实跑出来的示范房间（脱敏、模拟数据明确标注），每个房间本身就是可 diff、可重放的活文档。导出前必须清掉密钥、个人路径与未公开业务内容。

**当前边界**：完成态已有 `CONCLUSION.md` + evidence + commit + 顶部交付单（目标、阶段、命令与退出码、改动文件、验收结论、commit）；交付单还没有导出与跨房间汇总。目标岛（房间名 / 一句状态 / 阶段与返工记录）已作为独立模块完成并投入打磨，后续按 dogfood 卡点继续迭代。

## 5. 群是产品的一等公民

一句话先给结论：**这个产品里唯一不可替换的对象是群（Room）。** bot 可以换、引擎可以换、模型可以换，群不能——它持有目标、讨论、证据与结论。

行业默认把 agent 当主体、把群当容器；我们反过来：**群是主体，agent 是席位。**

直接后果：产品的每一项能力都必须能在"群"这一层说清楚。下面七个面，就是群的七个设计维度，也是全部的创新点所在。

**先回答一个问题：单个 agent 到底做不到什么？**

这是整份设计的根据。说清楚四条，其余都是装饰：

| 单 agent 做不到 | 为什么是结构性的 | 群怎么做到 |
|---|---|---|
| **独立验收** | 同上下文、同模型家族、同作者，判断无法与产出真正分开 | 盲审 + 独立会话 + 默认不同厂商引擎，单 CLI 时明示降级（§5.6） |
| **分权** | 提议、执行、批准发生在同一个主体里，"自己批自己"无法避免 | 席位分离、三档权限，提议者不能批准（§5.3、§8.6） |
| **异构工具** | 一个 CLI 只有一套工具与沙盒，不能用 Codex 的补丁能力加 Claude 的长上下文 | 每席可选不同引擎（§10.5） |
| **故障隔离** | 上下文一旦被带偏，整个任务一起偏，没有第二双眼睛 | 独立会话 + 一人一 worktree（§10.4） |

但要说清楚：**群不会让模型更聪明。** 等算力下辩论不优于单 agent（§5.10）。群带来的是**可验证、可分权、可隔离**，不是更高的智商。这是本设计与所有"多 agent 更聪明"叙事的根本区别。

### 5.1 群的载体：房间即工作空间（真创新）

**是什么**：一个房间 = 一个可交付的工作空间，默认是一个 git 仓库目录；房间记录固定在房间根的 `.crew/rooms/<room-id>/`，不要求房间根一定是 git 仓库。`.crew/rooms/<room-id>/` 下有 `transcript.jsonl`、`BRIEF.md`、`GOAL.md`、`CONCLUSION.md`、`decisions.md`、`evidence/`。git 实现下，一场讨论结束 = 一次 commit；非 git 实现下以房间记录与交接包留痕。

```
.crew/rooms/<room-id>/
  BRIEF.md          # 人；目标、约束、已决事项（运行时只在不存在时生成初稿）
  GOAL.md           # 运行时投影：阶段与状态，每回合重写
  CONCLUSION.md     # 运行时投影：完成结论
  transcript.jsonl  # append-only；先写并 fsync
  events.jsonl      # append-only；阶段、复核、审批、提交的治理轨迹
  decisions.md      # 人维护；运行时不写
  evidence/         # 命令、退出码、输出、diff

<data>/worktrees/<room-id>/planner|verifier/   # M3 首版：队长克隆、验收副本；executor worktree 作为房间交付目录
```

**worktree 在源仓库之外。** M3 首版把 executor worktree 作为房间交付目录；`.crew` 与代码同目录，但 diff 和候选提交排除 `.crew`，避免污染交付内容。完成时的结论 commit 会包含 `.crew/rooms/<id>/`，让房间记录随分支走。

**git 不是本体（设计裁定）**：房间的本体是工作空间 + 记录，git 只是当前的默认工作区实现。房间可以是一个普通目录，装文档、数据或其他产物；版本控制、分支隔离、候选 commit、合并与 diff 都通过 Workspace 端口提供，缺失时按能力降级，不把 git 写进业务规则。端口与迁移顺序见 §10.4.1。

**为什么别人没做**：DS Bot 的群有独立文件夹，OpenMausBot 的 bot 有 workspace，但聊天记录和代码始终是两套东西。云端个人 agent 更是把一切锁在自己的 VM 里。

**为什么强**：讨论变成可 diff、可回滚、可 clone 的产物。git 实现下，完成后任何人 `git clone` 该分支，就能重放整场讨论；普通目录实现下，房间记录与交接包承担同样的留痕职责，但没有分支与 commit 可追溯。

### 5.2 群的状态：游标可见（真创新）

**是什么**：每个成员有一个 `last_read_seq`。落后太多时不再补全量，改发**交接包**（BRIEF + 最近 N 条 + "其余在 transcript.jsonl 里，用工具读"）。

**为什么别人没做**：Grok Bot 的 Bot 互相私聊、Cue 的群聊交接，都没有把"谁读到了哪里"变成一等状态。

**为什么强**：这是唯一能让人一眼看懂"谁跟上了讨论"的机制，同时降低上下文成本，并解决新成员中途加入。

### 5.3 群的席位：工位不是人格（新）

**是什么**：一个席位 = 职责 + 写入范围 + 引擎 + 发言配额 + 是否 verifier。名字和语气只是薄薄一层。

**为什么别人没做**：Grok Bot 把 Bot 做成"数字同事"、Cue 做成生活助理，卖点都是人格与记忆；开源框架的 role / backstory 也是人格优先。

**为什么强**：

- **换人不丢上下文**：新人接的是工位和游标，不需要"模仿前任说话"
- **可审计**：每条消息都带作者与引擎，责任可追
- **可替换**：引擎挂了换一个，群不散
- **成本可控**：配额挂在席位上，不是挂在"人"上

**人也是席位。** 人不只是"最后点验收的按钮"，而是一个常设席位：`kind: human`，权限是 read + write（改 BRIEF、加约束），没有引擎，不被 @ 也能看到全部消息。三种动作：

- **补约束**：写进 `constraints`，不重开目标
- **改 done**：触发 `revise`，已通过的阶段保留
- **最终否决**：任意阶段都可以停下整个群

人不占发言配额，也不参与轮次——否则群会学会绕过人。人席位在界面上始终可见，不折进"成员管理"。

**UI 约束**：AI 席位表默认不出现。点某个机器人才看到它——这是 §2.3 渐进披露在群上的具体落法。你的席位不进表，它就是输入框。

### 5.4 群的资源：发言权是预算（组合创新）

**是什么**：每人每场有发言配额。`[pass]` 合法且免费但计入轮次。配额用完只能旁听，被 @ 才能开口。

**为什么算创新**：开源实现都在优化"少叫人"，都在回避多人讨论的成本；云端产品靠不透明路由压成本。没人把发言当资源管理。

**真正的好处不是省钱**：预算耗尽是一个自然的收束信号——"该出结论了"。

**当前实现**：成本硬闸门已落；席位有 `speakBudget` 字段并展示，但回合强制未接。

### 5.5 群的会议：可分叉、可并排（组合创新）

**是什么**：任意一轮可以 fork 成两条支线，各自跑完，对比结论与 diff。

**技术**：Claude 有 `--fork-session`；房间层面只是复制目录 + 新 seq 域。

**当前实现**：可从进行中/已完成房间 fork 出新房间；两条支线并排比较的会议界面未做。

### 5.6 群的边界：隔离与独立性（真创新）

**是什么**：三条硬边界——

1. 执行阶段一人一个 `git worktree`
2. 产出者与验收者**默认必须是不同厂商引擎**；只有一台 CLI 时显式降级（见下），并在验收卡标注
3. 对外动作必须过审批桥；审批桥独立判定，不与被审对象共享上下文

**为什么是群的能力，不是 agent 的能力**：隔离、独立性、审批都是**关系属性**，单个 agent 自己提供不了。云端产品恰恰在这里最弱——Grok Bot 所有 Bot 共用一台云电脑（官方直言别拿它当安全边界），Dots 的审批是产品约束而非结构约束。

**为什么强**：同模型自审有系统性盲区。换厂商验不是"模型多样"，是**认知独立**——这是"多 CLI"唯一无法被单模型产品复制的价值。

**独立性分三级，必须显示给用户：**

| 级别 | 条件 | 说明 |
|---|---|---|
| `vendor` | 不同厂商引擎 | 默认。最接近结构独立 |
| `model` | 同厂商不同模型 | 可用，但要在验收卡上标"同家族" |
| `none` | 只有一个 CLI | 只剩盲审与命令两个锚，必须标"独立性降级" |

只有一台 CLI 是常态，不是例外。**不标注就是骗人。**

运行时按 `rooms.independence` 记录实际级别，模板里的 `engine_constraint` 只是默认值：**可以降级，不能悄悄升级**。降级时验收卡上必须出现"同家族"或"独立性降级"。

**独立性有上限：共模失败。** 换厂商只能降低同错的概率，不能消除：不同模型可能在同一批训练语料上形成同一盲区，或对同一类陷阱犯同一种错。两个引擎都说"通过"，不等于正确。所以自动化验收给的是**概率**，不是保证；最终验收必须由人点（§9.4）——这不是流程礼貌，是防共模失败的承重墙。产品话术只能说"降低了没被发现的概率"，不能说"验证过就没问题"。

**当前实现**：worktree/审批/盲审/多验收已落；无第二可用引擎时显式降级，跨厂商仍是环境依赖。



### 5.7 群的交付：验收是命令（执行优势）

**是什么**：交付型阶段的 `acceptance` 必须是可执行命令。verifier 在一次性集成副本里执行，证据是退出码 + 输出 + diff。**没有命令的交付型阶段不允许 active；决策型阶段则必须有人点过一次。**

**为什么只算执行优势**：CrewAI 有 guardrails，personal-agent 和 DS Bot 都有证据门禁，概念不新。但它们的证据允许自由文本，模型容易自述过关。

**我们做硬的**：命令是唯一的 pass 凭证。完整设计见 §9。

### 5.8 群带来的三类优势

| 对象 | 优势 | 由哪个面支撑 |
|---|---|---|
| **用户** | 只说目标、答 ≤3 个问题、点一次验收 | 席位默认、对齐、一键验收 |
| **结果** | 可验证：命令 + 独立审查 + 证据在仓库里 | 交付、边界 |
| **成本与隐私** | 用已付费的 CLI；仓库与讨论不出本机 | 边界、预算 |

**对结果的那一条最关键**：群里每个人看到的是同一份真相（房间），不是各自被喂的摘要。

### 5.9 先立住哪三个

1. **房间即仓库 + 证据**——群是产物的物理基础
2. **游标 + 圆桌**——用户能直接感知的"小队感"
3. **跨厂商评审**——唯一无法被复制的壁垒

前两个决定产品像不像"工作小队"，第三个决定别人能不能抄。其余创新（fork、发言权预算）都是在这三者之上的放大器。

### 5.10 研究证据：哪些创新站得住

2025–2026 的证据对这份设计既支持也打脸，分开说。

**支持我们的三条**

| 证据 | 结论 | 对应我们的设计 |
|---|---|---|
| **MAST**（NeurIPS 2025，7 个框架、1600+ 轨迹） | 多 agent 失败率 41%–86.7%；**79% 的失败是规范与协调问题**，不是模型或工具。高频项：步骤重复 15.7%、不知何时停 12.4%、推理与行动不一致 13.2%、验证缺失或错误合计 17% | 正好对应我们的三件产物：`BRIEF.md`（规范）、单一 Assignment 生命周期 + 游标（协调）、`acceptance_cmd` + 独立 verifier（验证） |
| MAST 的消融 | 补角色规范 +9.4%，加验证 +15.6%，但仍远未解决；显式 verifier 的框架验证层依然薄，ChatDev 正确率仅 33.33% | "有 verifier"不够，必须**命令化 + 独立引擎**。我们的硬规则有据可依 |
| **LLM-as-judge 偏差研究**（EMNLP 2025 / IEEE Access 2026） | 自偏好真实但控制质量后变小；**家族偏好独立存在**；风格、长度、作者身份都会干扰评分；推荐"家族多样 + 客观锚点"的评审团 | 跨厂商评审方向正确，但必须补两条：**盲审**（隐藏作者与引擎）+ **客观锚**（命令） |

**必须改口径的一条**

等算力下比较多 agent 辩论的 2026 年研究结论很一致：**单 agent 追平或超过多 agent**（Tran & Kiela, COLM 2026；"Perspectives Without Independence"）。辩论收益几乎全部来自**第一轮交换**，之后是共识锁定与谄媚（最高 95%），同质团队在部分条件下甚至负协同。

所以：

- 不能卖"圆桌让答案更聪明"
- 只能卖"圆桌让工作可分工、可验收、可追溯"
- 讨论的价值集中在**第一轮**，之后应当收敛而不是继续聊
- "发言权预算"和"连续 6 轮无产出暂停"因此是对的，不是保守

**由此得到两个新的创新点（建议）**

1. **先盲后圆（Independent-first round）**
   评审与设计类议题，第一轮不注入别人的发言，各自独立给判断；第二轮才读最新群、开始圆桌。理由：辩论的收益来自首轮独立答案，而"开口前读最新群"会制造从众。
   实现成本极低：第一轮不拼 delta 消息即可。协调类议题仍走原流程。
   → 这可能是产品里唯一有论文直接支撑的交互创新。

2. **盲审 + 客观锚（Blind review with an anchor）**
   verifier 拿到的 diff 不带作者与引擎信息；通过与否先由 `acceptance_cmd` 决定，模型只解释差异。理由：作者身份本身就会移动评分，而命令是唯一不受风格影响的锚。

**还要承认的边界**

这些论文多在中小模型与推理基准上做，产品级证据仍然薄。我们的验证清单只能证明机制正确，证明不了"团队比单 agent 产出更好"——后者要等真实用户数据。

## 6. 优秀设计理念：照着抄的 28 条

### 6.1 来自 personal-agent（机制层）

| # | 理念 | 为什么对 |
|---|---|---|
| 1 | **system 逐字节稳定**：会变的东西一律作为消息追加 | 前缀缓存命中的硬前提 |
| 2 | **双预算分开**：`maxSteps` 与 `maxToolCalls` 分开计 | 一步可能发多个调用 |
| 3 | **到阈值二选一**：`compact` 或 `switch` | 反复压缩＝摘要的摘要，越来越虚 |
| 4 | **压缩后必须留三样**：system、原始请求、已加载技能正文 | 否则忘了为什么在做这件事 |
| 5 | **记忆以文件为真相**：Markdown + 索引，可读可改可撤销 | 数据库只是索引 |
| 6 | **审批是一等实体，超时不是静默 deny** | 伪造"用户拒绝"会让 agent 学错因果 |
| 7 | **dispatch 后不重试**，状态不明标 `uncertain` | 重复副作用比失败更糟 |
| 8 | **角色与沙盒是两层** | agent 给自己提权是最短的越权路径 |
| 9 | **消息传 envelope，不传 transcript** | 接收方自己取上下文，token 才不爆 |
| 10 | **状态不进 system** | 状态一变缓存就废 |

|---|---|---|

- 私有 bot：独立目录、不能当 lead、不能进群

## 7. 照搬 vs 重写

### 7.1 基座复用：OpenMausBot OSS

**结论：以 OpenMausBot OSS 为基座 fork，而不是把 runtime 抄进 Lodge。** 实测 `claude.ts` 与 `acp/core.ts` 各 44 条 import，牵扯 config、procs、auth、catalog、engine home 一整片；抄出来等于维护一个私有分叉，也拿不到上游的引擎更新。

基座里**保留并接线**：

| 模块 | 能力 | 我们做什么 |
|---|---|---|
| `server/runtime/` | Assignment 全生命周期、事件重放、10 条不变量、问题挂起、结果信封 | 宿主 `TurnRunner` 接房间回合；**不改生命周期与不变量** |
| `server/drivers/` | 原生 Claude/Codex、ACP 多引擎、工具事件、重试、限额 | 席位 → botId 的引擎绑定；新增引擎只加 driver 或 `customAcp` |
| `server/engine-*` | 安装、版本探测、更新、握手、限额 | 不改 |
| `claude-auth-*` / `codex-login` / `device-auth` | 登录、OAuth、失效恢复 | 不改 |
| `server/model-catalog/` | 模型目录与探测 | 不改 |
| `message-db` / `thread-events` / `sse-fanout` | SQLite WAL、事件表、SSE 背压/重连 | `thread` → `room` 的 id 映射 |
| `permission-proxy` / `auto-approve` / `questions` | 权限请求、审批、人工提问 | 席位权限表映射到 approval mode |
| `server/room-{context,cwd,folder,holds,lines}` | 房间成员上下文、固定目录、@ 持有 | 直接用于 Room 会话 |
| `electron/` + `electron-builder.yml` | 窗口、生命周期、打包、更新 | 换品牌、删无关面板 |

> **当前 P0**：基座是独立仓库 `crew-chat-base`（8799），通过 HTTP 接入；没有接 runtime Assignment，房间回合用基座群消息与 bot 回合。下面是正式 fork 后的目标接线。

基座里**删除或关闭**：`enterprise/`（商业授权，一行不进）、完整产品 UI 与约 3,300 行 `store.tsx`、`browser/computer/phone/email/meetings/postiz/connectors/cloud/companion/mobile`、`routines/sentinel/decider`（保留接口不启用）、以 `state.json` 为唯一存储、群日志 60 行上限。

**新增**：`server/crew/`（房间即仓库、阶段门禁、证据、席位模板）、`server/crew-host.ts`（只装配需要的模块）、当前 `ui/` 迁入、`templates/`。

扩展只有一条路径：

| 要加什么 | 改哪里 | 动核心？ |
|---|---|---|
| 新引擎 | 新 driver + `drivers/builtIn.ts` 注册，或 `customAcp` 配置 | 否 |
| 新模型 | `model-catalog/` | 否 |
| 新席位 | 席位模板（角色 + 权限 + 引擎绑定） | 否 |
| 新阶段类型 | `server/crew/stages` | 产品层 |
| 新验收方式 | `server/crew/acceptance` | 否 |

**两天 spike 判据**：基座能启动、我们的 UI 能接上、一个房间跑一次真实 Claude turn、证据落盘。不满足再退回“按模块移植”，但那意味着接受私有分叉的成本。

**Spike 结果（2026-11-11，通过）**：基座 fork 在 `8799` 启动；Lodge 原型 UI 经 `server/base.js` 适配层接上（原型仍独立运行，尚未迁入基座）；基座群 `crew-spike` 映射为实时房间，从房间输入框发消息后真实 Claude turn 完成 Write `hello.txt`，turn digest 被捕获为 evidence JSON（`meta.kind: 'turn'`），产物 sha256 与磁盘文件一致。S1 判据“关掉重开一致”已满足；S2 产品层与 S3 验收链路尚未开始。

**Claude-Bot / DS Bot：优秀设计可复用，保留许可与归属；不继承 DSH 耦合。** 当前 UI 为 Lodge 自写；`ui/src/dsbot` 已在 P0 删除整包 vendored。需要某块组件或 CSS 时，可以按模块复用，保留 Apache-2.0 `LICENSE`、`NOTICE` 与文件头；不引入 DSH 宿主、插件、store 强耦合；不 import `sidebar.js`；不把 `createElement` 改写成 TSX；不引入 Tailwind。

**personal-agent** 继续作为机制参考：envelope 语法（`[From <who> · <what> · <authority>]` + `escapeNotes`）、稳定 system、双预算、压缩后保留三样。

许可证：OpenMausBot 与 Claude-Bot / DS Bot 均为 Apache-2.0，保留根 `LICENSE`、`NOTICE` 与文件头；`enterprise/` 是单独商业许可，删除；OpenMausBot / MausBot 名称与吉祥物是商标，产品只用 Lodge 品牌。

### 7.2 必须重写的 6 件事

| 照搬会怎样 | 为什么必须重写 |
|---|---|
| **OpenMausBot 的完整产品 UI 与 3,300 行 store** | 它绑 bot-as-person 与整套页面；我们的主体是房间。只复用底层事件，UI 与状态层自写 |
| **各家的会话模型**（每 bot 一个长会话） | 与“房间持有真相”冲突。成员只记游标 |
| **各家的群聊默认策略** | 与产品定位冲突。圆桌必须是一等模式 |
| **personal-agent 的纯 API runtime** | 我们要 CLI 的登录态与订阅 |
| **通用 Memory 系统** | CLI 自带记忆，再叠一层会互相打架 |
| **上游的云电脑、连接器、routines/sentinel 等产品面** | 与首版无关，扩大攻击面与打包体积；Electron 壳保留，设置项越少越好 |

### 7.3 一个判断

**代码可以抄，产品不能抄。** 上面 28 条解决的是"正确性"，不是"是什么"。云端的六家都在解决"一个人怎么被服务得更好"；Lodge 解决的是"一件需要多人分工的事怎么被交付"。这一格必须自己写。

## 8. 产品形态：一屏，三步

### 8.1 默认那一屏

```
┌──────────────────────────────────────────────┐
│  给 CLI 加 --verbose                       ⌄  │  ← 目标岛：房间名
│  ● 实现中 · 阶段 2/3 · 实现          [继续]   │  ← 一句状态 + 一个主动作
├──────────────────────────────────────────────┤
│  验收    测试覆盖到 --verbose 的分支了吗？     │
│  执行    已补 3 个用例，见 evidence/e12       │
│  ✔ npm test (exit 0)              [查看证据]  │
│  执行    [pass]                               │
├──────────────────────────────────────────────┤
│  [ 继续 ]  [ 暂停 ]                 高级 ⌄    │
│  ┌────────────────────────────────────────┐  │
│  │ 说点什么，或直接交办…                    │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

编制压成"N 人在做"，任务板压成一句状态。**只有点开"高级"或点某个人，才会看到工位、引擎、游标、预算。**

点目标岛展开：阶段步进器（每阶段一格，已过打勾、当前高亮、可点回看），选中阶段下面是"做到什么算过"、返工记录、证据、每个席位的任务；底部折叠"目标与检查"（objective / done / constraints）与暂停、继续、停止。目标在房间里始终可见，不进设置页（§9.7）。

你不在成员列表里——那个输入框就是你的席位。你随时能插话、加约束、最终否决，不计轮次（§5.3）。

时间线主视线只有三种东西：**对话、结果卡（证据 + 验收）、阶段里程碑**。派活、心跳、原始回合与整房结论收进一条“过程记录”折叠；证据和验收结论保留一键可查。

阶段门只在当前阶段真的需要人时出现：等你确认、等你设验收命令、验收退回等你返工，或没有验收席位时等你签字。等待复核、暂停、已有验收席位的签字都由状态句和结果卡承担，不常驻在输入框上方。

全局的第一个房间不是群，是**调度台**：同一个壳，时间线换成收件、路由建议与摘要（§8.8）。你永远先落在它这里，但它不会替你做决定。

### 8.2 建队：30 秒三步

1. 输入一句话（可以很糙："给 CLI 加个 verbose"），可选给房间起个名字；留空就用目标自动命名。仓库可选
2. 规划师先自己查仓库与上一轮记录，给出一张**开工卡**：**done（做完的样子）、三人分工、验收方式**，外加真正要你拍板的问题（≤3，每个带推荐答案）；你可以只回"都按推荐"
3. 人一次确认：按方案开工；要改就回到目标或答案，不进入手动选人。确认后直接开工，不再二次对齐。BRIEF 默认折叠，只展开 done 那几条

**对齐、编队、验收方式是一张卡。** 不拆成"先推荐编制、再对齐一次"；人只确认一次，减少一次打断。当前产品默认固定三人：规划师、执行者、验收员。业务只校验硬约束（至少一个执行、验收独立性、权限派生、1–8 席与并发/成本上限），席位权限仍由角色派生。

**单人、自定义编制和模板暂不开放。** 它们是保留的扩展接口，代码还在，但不进入首屏、不由 Lodge 自动选择，也不在开工卡上给用户做选择题。重新开放时必须单独过权限、验收独立性和成本门禁。

**人工验收（manual）房间不挂验收席位。** 要独立复核就补一条可执行验收命令；两者不能同时成立，业务层 fail closed。manual 房间的产物就绪证据只代表“可以交给人看”，不代表命令通过。

### 8.3 一次讨论的样子

- 一次一人，消息按 seq 排列
- 评审类议题第一轮不注入他人发言：各自先写结论，再公开对齐（§5.10）
- 你随时可以插话、加约束、否决；不计轮次
- `[pass]` 显示为极淡的标记，不占正文
- 跑题由 broker 拉回；连续 6 轮无产出 → 暂停，标"等你说话"
- 每轮一张**结论卡**：本轮结论 / 下一步 / 需要你决定的事
- 产出 patch 时 diff 内联
- 游标默认不显示，点开某人才看
- 成员之间的私聊不进主时间线，只在结论卡里体现（v1.1；首版不做私聊）

### 8.4 高级里有什么

当前高级面板可看/可改：席位引擎绑定与降级原因、席位角色与权限、每个席位的发言配额（只读，尚未强制）、房间预算（可改）、未开始阶段编辑、MCP 熔断恢复、历史目标、交接包导出。建后加/移除/改角色是封口扩展，当前只显示席位表，不提供入口。

尚未做成高级控件：逐席位模型选择（当前只显示基座可用实例与默认模型）、写入范围编辑（由角色派生）、讨论模式、主动程度。分叉是房间操作，不是高级参数。

原则：**高级里可以复杂，主路径必须只有一条。**

### 8.5 一个群的一生

群是产品的一等公民，所以它的生命周期比 agent 更长、也更明确。

| 阶段 | 群的状态 | 用户动作 |
|---|---|---|
| 建群 | 只有一个目标，还没有成员 | 说一句话 |
| 开工卡 | `drafting`，规划师看完仓库，给 done + 分工 + 验收 + ≤3 个问题 | 答 ≤3 + 确认一次 |
| 开工 | 按方案席位就位（1–N），BRIEF 已写，直接开工 | 点"按方案开工"或"改目标" |
| 圆桌 | 讨论中，游标推进 | 不用管；想插手就直接说 |
| 执行 | 阶段 active（每个执行自己的 worktree；多执行可并行） | 不用管 |
| 验收 | 证据齐全，等你判定 | 点"接受"或"重做" |
| 归档 | `complete`，生成 commit 与 `CONCLUSION.md`（`decisions.md` 归人） | 没有动作，群还在 |

关键：**群的每个状态都有且只有一个"下一步动作"给用户**。没有动作的阶段，界面上就不该有按钮。

群也不是一次性的。一个群跑完一个 Goal 可以接下一个 Goal，人的 `decisions.md` 与运行时的 `CONCLUSION.md` 一起留在仓库里。这是"房间"和"会话"的根本区别：**会话会丢，房间会积累。**

房间列表只为真正卡在人的房间亮起一个信号：待确认 / 待回答 / 待签字 / 待复核 / 退回 / 待设验收命令；不是未读数，也不为每条 bot 消息点亮。

### 8.6 群模板：内置一个，可一键导入

**结论：不做"工作模式"开关，做模板。只内置一个，但模板是一等数据类型。**

- **固定三人小队**：对外显示 **规划师 / 执行者 / 验收员**，内部角色仍是 Planner / Executor / Verifier。建房默认就是这三人；单人、自定义编制和模板入口暂不开放。
- **可导入**：`.crew.yaml` 拖进窗口即建群；导出即分享。
- **不做模式**：模式会分叉运行时语义；模板只改数据（席位、提示词、权限、产物）。runtime 永远只有一条代码路径。
- **不做市场**：先支持本地文件与复制。

模板包含五样：

| 字段 | 作用 |
|---|---|
| `seats` | 名称、工位、引擎、权限、系统提示词 |
| `permissions` | read / exec / write 三档，由沙盒执行 |
| `workflow` | 谁能 @ 谁、什么事件推进、哪些规则由运行时强制 |
| `artifacts` | `BRIEF.md` / `GOAL.md` / `CONCLUSION.md` / `evidence/` 的归属 |
| `announcement` | 群公告，首次进入时展示 |

**权限是三档，不是两档。** 这是对"Planner 只读、Verifier 仅可查看"的一处修正：

| 席位 | read | exec | write |
|---|---|---|---|
| Planner | ✓ | ✗ | ✗ |
| Executor | ✓ | ✓ | ✓（仅自己 worktree） |
| Verifier | ✓ | ✓ | ✗（中间产物落临时副本，不合并） |
| 你（human） | ✓ | ✓ | ✓（不受限；改 BRIEF、加约束、最终验收） |

Verifier 不能只是"仅可查看"——它必须自己跑验收命令。但它也不该有源码写权限。所以是 **read + exec，write = none**。

**当前**：权限已声明并在启动时校验；工作区隔离已落（planner 克隆 / executor worktree / verifier 临时副本）；工具审批桥已落——基座权限卡经 Engine 适配层映射为 read/exec/write，`live.js` 按席位权限 allow/deny，planner/verifier 的 Write/Edit/MultiEdit 已被真实房间拒绝。外部动作再走一层人工审批：`external-actions.js` 识别 push/发布、安装依赖、删除、对外发送、提权、网络/远端命令，命中后写 `room.approvals` 并挂起基座权限卡，人在时间线点允许/拒绝后才回答；暂停、停止、断绑、重启会使其失效。`exec` 仍可在临时副本里写文件，不是通用文件系统沙箱。多验收席位已接：每个验收席位拿到同一轮验收证据独立复核，全部 PASS 才允许签字，任一 REJECT 立即打回并取消其余等待中的复核。`approval`、`mcp`、`skills` 已留扩展缝，默认关闭；MCP 只存 server 名，planner/verifier 不放外部工具。

**GOAL.md 归运行时，不归 Executor。** 让执行者维护清单在纯聊天工具里可行；在这里状态是运行时的事实，`GOAL.md` 只是每回合重写的一份投影。原因很简单：**让被验收的人记账，等于没有账。** 模板只保留兼容约定（Executor 追加"待验收 + 证据"），产品内由 runtime 强制。

**模板里的提示词只解释规则，不承担规则。** 每一句"禁止"都要有一条运行时强制：

| 提示词说的 | 运行时做的 |
|---|---|
| 默认一次只派一个 | `max_active_assignments: 1`（可调） |
| 带证据才算完工 | 无 `evidence` 的 submit 被拒绝 |
| 只有 Verifier 能判完成 | 状态机只接受 verifier 的 PASS |
| 连续三次 REJECT 停 | `max_rejects: 3` → `waiting_on_user` |
| 不改目标 | 只有人类能发 `revise` |

设计约束：**提示词负责让模型理解，权限负责让模型做不到。**

**申诉一次，然后升到人。** Executor 对 REJECT 有异议时，可附证据申诉一次；Planner 裁决；仍不一致则 `waiting_on_user`。没有申诉通道，Verifier 就成了独裁者，双方会开始互相博弈而不是对事实负责。

模板文件：[`templates/delivery-triad.crew.yaml`](../templates/delivery-triad.crew.yaml)

### 8.7 不做部门：用编制与工作区替代

"部门"看起来是自然需求，其实是四个不同需求被打包在一起：

| 真实需求 | 部门式的解法 | 我们的解法 |
|---|---|---|
| 复用一组席位 | 部门成员 | **编制模板（Roster）**：保存一组工位，一键套到新群 |
| 多个群共用仓库 / 凭据 / 预算 | 部门资源 | **工作区（Workspace）**：一个仓库 + 默认引擎 + 预算上限，可被多个群引用 |
| 侧栏整理 | 部门树 | **分组 / 文件夹**：纯整理，无权限语义 |
| 多人权限边界 | 部门权限 | **组织（Org）**：只在多人时出现，只管人、凭据、账单，不管任务 |

**为什么不做：**

1. **语义冲突**：部门是长期组织，群是一次交付。我们已经把"长期"放在"群可接多个 Goal + 人的 `decisions.md` 累积"里。再加一层，用户会问"这个任务属于群还是部门"。
2. **违反一条成功路径**：多一层树，就多一次"我该建在哪"的犹豫。
3. **没人需要**：Grok Bot 有 Chief of Staff 也没有部门；CrewAI 只有 Crew；云端个人 agent 更没有。部门是企业采购语言，不是使用语言。

层级只在需要时出现，日常只看得到 Room：

```
Org（多人时才有）
└─ Workspace（仓库 + 默认引擎 + 预算）
   └─ Room（群，日常唯一入口）
      └─ Goal → Stage → Assignment
```

原则：**组织管资源，群管交付。** 任何"这个任务归谁"的问题，答案永远是群，不是部门。

### 8.8 一个入口，不是一个大总管

用户的原话是"有事都先找你，你判断该交给哪个机器人、哪个群，通知它们开工，盯好进度，做完把结果汇总给我"。这个需求是真的：**入口只能有一个**。一个人面对十个群，第一件事不是派活，而是不知道该敲哪扇门。

但把入口做成一个**能自己派活、自己判断完成的总管**，会把前面七节的设计一次推翻：

- 它要判断"谁最合适"，就得读所有群的上下文 → 隐式跨群读权限。**只读投影可以，读全文不行**
- 它要"通知开工"，就得能创建 Assignment → 绕过了群自己的 Planner 与人的确认
- 它要"盯进度、汇总结果"，就会产出**没有证据支撑的叙述** → 又变回 LLM 自评
- 一旦它判断错了，错的是全局，不是某个群

所以形态是：**入口只有一个，但入口不是总管，是前台。**

注意这里否定的只是"全局总管"。群内的规划师仍是产品角色（§4.2）：在一个目标内部，它负责拆阶段、派活、复核。区别在于规划师的权威来自**这个群的目标与权限**，范围到群为止；调度台的权限只有"建议"。§9.8 的 Supervisor 派活是群内阶段协议，不是这个调度台的自动路由。

**调度台本身就是一个 Room。** 不是新对象，不是新部门，只是 `kind: dispatch` 的群：有自己的 `transcript.jsonl`、自己的事件；人的决定可写 `decisions.md`。你今天能看到它为什么把这件事交给了 3 号群——因为它当时就是这么说的，记在案上。**路由决策必须可审计，否则"智能派活"和"随机派活"对用户没有区别。**

它只做四件事：

| 动作 | 做什么 | 不做什么 |
|---|---|---|
| **收件** | 所有"我不知道该找谁"的话先落在这里，成为一条带时间戳的请求 | 不直接开任务 |
| **建议** | 给出候选群 / 席位、理由、需要的权限、预估阶段数；理由必须引用各群的公开投影（Goal、当前阶段、最近证据、未决问题） | 不替目标群重写 Goal |
| **确认** | 你点一次，才创建 Assignment 并唤醒目标群 | 不能自己点 |
| **汇总** | 从 `goals` / `goal_stages` / `assignments` / `evidence` / 未决问题生成摘要，每条结论都带来源 | 不做自由叙述，不替你判断 PASS |

**四条禁止**，写进不变量，不是提示词：

1. **不写仓库**。调度台没有 `write` 权限，它的 worktree 不存在。
2. **不代替 Verifier**。它可以引用"3 号群的 Verifier 给了 PASS，证据是这条命令 + 退出码"，但不能自己说"通过了"。
3. **不改 `done`。** 目标对齐与最终验收永远在目标群里、由人拍板。
4. **不持有跨群写权限。** 它能读各群投影，是因为投影本来就是给侧栏看的；要动某个群，只能通过"确认 → 目标群收到一条 Assignment"这一条路。

一句话：**它建议，你确认；它汇总，你验收。**

**当前实现（2026-11-13）**：首屏只保留三块——有请求时的“需要你确认”、房间摘要（阶段/最近证据/是否等你）和输入框；资源统计、Token 趋势、导入导出与已处理记录收进折叠的“系统状态”。空区块直接不显示，避免“没有新的请求”“还没有处理过的请求”占位。**单房间且没有待确认请求时，启动直接落在房间**；调度台仍可从侧栏或左上角 Lodge 进入，多房间或有待确认时才默认落在调度台。

**摘要不是模型写的作文。** 汇总页的每一行都必须能点回来源：这条来自哪个群、哪个阶段、哪条证据、哪个未决问题。做不到这一点的摘要，比没有摘要更危险——它看起来像结论。这也是我们和 Grok Bot 的 Chief of Staff 的差别：那边是一个有人设的主管在跟你说话，这边是一个把路由理由和阶段状态摆在桌上的调度台。

**分两步上线，不要一次做满：**

- **第一步（只读）**：收件箱 + 路由建议 + 一次确认 + 投影式摘要。建议可以是启发式的（关键词、仓库、最近活跃群），不需要模型也能工作。
- **第二步（低风险自动）**：只对白名单里重复出现过的请求类型（"跑一下测试"、"看看昨天那个 PR"）允许免确认，且必须留一条可撤销的 dispatch 记录。默认关闭；**首版只做第一步，第二步不接**。

## 9. Goal：先对齐 done，再拆阶段，逐段验收

### 9.1 三个不同的问题

| 问题 | 什么时候问 | 产物 | 谁拍板 |
|---|---|---|---|
| **什么算做完？** | 开队之前 | `BRIEF.md` 的 done + 每阶段 acceptance | **人** |
| **这一段算不算过了？** | 每个阶段结束 | 交付型：命令 + 退出码 + diff；决策型：决策记录 | 交付型由 Verifier 按命令判；决策型由人点一次 |
| **整件事算不算成了？** | 全部阶段之后 | 总结 + 证据索引 | **人** |

第一列是**目标对齐**，第二列是**逐段检查**，第三列是**成果验收**。三者缺一：

- 只有验收没有对齐 → 每次验收都在重新定义"做完"
- 只有对齐没有验收 → done 变成一纸空文
- 只有逐段没有总验收 → 每段都过，整体却不是你想要的

**完成权在人，不在 agent。**

### 9.2 对齐：只问真正要人拍板的分叉

- 事实是规划师的活，决定是人的：能从仓库、文档、上一轮 transcript 查到的，**不许问人**
- 只问真正要人拍板的分叉，**一轮编号提问**：每问写清推荐答案与理由（一行），备选各几个字；人可以回"都按推荐"或"2: B"
- 答完若开了新分叉，再问一短轮；清楚即止，不凑问题
- done 必须**可判定**：每条要么对应一条命令，要么对应一个明确产物
- 结果写成 `BRIEF.md`，人确认后才进入编队
- 对齐发生在时间线里，不是设置表单：问题、答案、最终目标都留在房间里（§9.7）

```markdown
# 目标：给 CLI 加 --verbose
done:
  - [ ] `npm test` 通过
  - [ ] `crew --verbose run` 输出每步耗时
  - [ ] 不带 --verbose 时输出与现在逐字节相同
non-goals:
  - 不改输出颜色方案
constraints:
  - 不引入新依赖
阶段:
  1. 调研与接口设计   kind: decision     产出 decisions/research.md，人点一次
  2. 实现             kind: deliverable  acceptance: `npm test`
  3. 回归与文档       kind: deliverable  acceptance: `npm test && ./scripts/e2e.sh`
```

注意第三条 done——"默认输出逐字节相同"。这种条目**只有在写 done 的时候才想得起来**。这就是对齐阶段的价值，也是 CrewAI 把 `expected_output` 设成必填的原因。

### 9.3 拆阶段：交付型一条命令，决策型一次确认

- 阶段数 3–5 个（P0 先落两段：目标对齐 + 交付；3–5 段在 M5）
- **交付型**阶段必须有 `acceptance_cmd`；没有命令的交付型阶段不允许 active。决策型阶段不设命令，但必须有人点过
- 每阶段指定 verifier；默认要求与产出者不同厂商，只有一台 CLI 时按 §5.6 降级并标注
- 阶段状态 `pending → active → passed`（产品层）；任务生命周期以基座 Assignment 为准：`queued → running → terminal`，中途可进 `needs_input` / `waiting` / `resume`。验收失败是 `rework` 事件，任务回 `queued` 并累加 `reject_count`；**不另造 working / reported / done 三态**
- 同一时刻只有一个 active 阶段；阶段内 active assignment 不超过 `max_active_assignments`（默认 1）

**阶段有两类，不要硬凑命令：**

| 类型 | 产出 | 判据 | 谁拍板 |
|---|---|---|---|
| **交付型** | 代码、文档、可运行的东西 | `acceptance_cmd` | 命令 + Verifier |
| **决策型** | 一份决策记录（选型、方案、放弃理由） | 记录存在且回答了 BRIEF 里的问题 | 人点一次 |

"调研与接口设计"这类阶段是决策型：`npm run typecheck` 只能证明代码没坏，证明不了调研做完了。**没有命令的交付型阶段不允许 active；决策型阶段不允许伪装成命令**（用 `echo ok` 凑数比没有更糟——它给了假证据）。

### 9.4 验收：证据是命令，不是自述

- `pass` 必须附证据：命令、退出码、输出摘要、改动文件。无证据**直接拒绝**
- 证据落 `evidence/`，transcript 里只放一行引用
- 不通过 → `rework` 写明缺什么，任务回 `queued`
- 交付型阶段自动跑命令；决策型阶段由人点一次；**总验收必须人点一次**——这是防共模失败的最后一道（§5.6），不是形式
- 用户中途纠偏 → `revise` 写进 `BRIEF.md` 的 `constraints`，再重建 SQLite 解析缓存；**已通过的阶段保留**

### 9.5 自动推进与停止

- 空闲且有 active Goal → 唤醒 lead 一次"goal check"，不是轮询
- 连续两次检查无进展 → `waiting_on_user`，**不再自动唤醒**
- 暂停时绝不唤醒
- Stop 中止整个级联，同时中断子任务

### 9.6 为什么这条是护城河

云端六家都在做"帮一个人把事做完"，不做"多个人交付一件东西并由人验收"。开源三家有 Goal，但停在"阶段 + 证据"，前面少了和人对齐 done，后面少了总验收归人。

补上头尾，产品语义就变了：你不是在看 agent 干活，你是在**验收一支队伍交付的成果**。

### 9.7 目标的呈现：目标岛

目标不是开场白，是常驻状态。它在房间头部占一块，**不新开页面、不进设置页**（来源：Claude-Bot 的 group goal 岛，`ds-bot/src/client/goal.js`）。

**收起时——房间名 + 一句状态 + 一个主动作**

```
给 CLI 加 --verbose                       ⌄
● 实现中 · 阶段 2/3 · 实现          [继续]
```

- 房间名一行；目标原文放在展开面板，不再把整段目标挤进标题
- 状态点 + 一句状态：已暂停 · 等你说话 / 验收退回 · 等你处理 / 目标达成
- 阶段号与阶段标题并在状态句里；不再单独放胶囊、轨道数字或头像
- 只有存在需要你处理的当前阶段时，右侧才出现一个主动作（处理退回 / 去验收 / 去签字）；没有就留空

**展开时——阶段步进器 + 当前阶段的全部凭据**

- 顶部一排阶段节点：已过打勾，当前高亮，点任一节点回看；过窄时只留节点不留数字
- 选中阶段显示：标题、"做到什么算过"（acceptance）、返工记录（谁打回、几次、上次意见）、通过后的证据、"回到当前阶段"
- 每席任务一行：席位头像（工作中脉冲、完成打勾、未开始变淡）+ 席位名 + 这一席具体做什么
- 底部左侧折叠"目标与检查"：objective / done / constraints；右侧是暂停、继续、停止（停止需二次确认，3 秒内不确认自动解除）；完成或停止后是"清除"

**当前实现（2026-11-13）**：收起态只留房间名、一句状态和当前阶段主动作；三问摘要、阶段轨道、任务头像行、徽章已从常驻头部移除（目标原文与凭据在展开面板/高级里）。展开面板保留阶段节点、返工与部分成功徽标、打回署名、证据链接、任务行与目标检查；当前阶段变化时自动跟随；底部控制条固定在面板内。数据从房间 JSON + verdict/evidence 消息派生，不依赖 `goals` 表。目标岛是独立模块 `ui/src/goal-island/`：`model.js` 把房间投影成标准 view（状态、进度、阶段、任务、证据、返工、控制项），`index.js` 只接收 `view` 与 `actions`，`island.css` 自带样式；房间页不把 room/store 传进组件。替换成更专业的目标岛时，只需提供同形的 view 与 actions。纯投影由 `ui/src/goal-island/model.test.js` 覆盖；组件树由 `ui/src/goal-island/ui.test.js` 用 esbuild + 假 React 渲染验证（收起/展开/导入/停止确认），测试 harness 改编自 Claude-Bot（Apache-2.0）的 `goal-client.test.js`。

**状态与数据一一对应，没有装饰性数字**

| 岛上显示 | 唯一来源 |
|---|---|
| 房间名 | `room.name`（目标原文在展开面板） |
| 状态句、阶段号 | `goals.state` + `goals.current_stage_id` + 各阶段 state |
| 当前阶段主动作 | `room.needsYou` + 当前阶段状态；没有需要你处理的事项时不显示 |
| 返工记录 | 当前实现：`verdict(pass=false)` 消息按阶段派生；目标模型：`goal_stages.reject_count` + `rework_feedback` |
| 证据 | `evidence`（`evidence/<messageId>.json` 可点开） |
| 每席任务与完成度 | `assignments.assignee_id` + `assignments.state` |
| "等你说话" | `goals.idle`（连续两次 goal check 无进展后置位） |

**为什么采纳**：它把 §9.1 的三问压成一句随时可读的状态——要去哪（房间名）、现在到哪（状态句）、要我做什么（唯一主动作）；凭什么算过、谁在做、返工意见都在展开面板里，不占首屏。用户在房间里任何时刻抬头就能回答，不必翻聊天记录，也不必打开另一个页面。

**改造了哪三处**（Claude-Bot 原样没有的）：

1. 证据可点开：岛上"证据"链到 `evidence/<messageId>.json`，不只是一行摘要
2. 返工意见署验收席位：打回必须来自 verifier，意见进 `rework_feedback`，不是管理员随口一句
3. 目标不进私有 JSON：`title / objective / done / constraints` 归 `BRIEF.md`，SQLite 只存带 `source_hash` 的解析缓存；阶段与任务落 SQLite，岛是只读投影；改目标走 `revise`，已通过的阶段保留

### 9.8 阶段内派活：规划师提议，系统执行（Supervisor，v1 已落 2026-11-12）

**形态。** 群里有一个主机器人（规划师），有任务时由它拆解、选择职能席位，并在群里 @ 对应席位派活。业界把这套做法叫 **Supervisor / orchestrator–worker**：一个主管负责拆解、分派与汇总，worker 只执行；@ 是显式派发（explicit dispatch / handoff）。Lodge 采纳它的交互形态，不采纳“模型直接指挥其他 agent”。

**契约：模型提议，系统执行。**

| 提案字段 | 含义 | 谁负责 |
|---|---|---|
| `stage` | 只允许当前 active 阶段 | 系统校验；不匹配直接拒绝 |
| `assignments[]` | 席位、这一步做什么、自查方式、是否并行、为什么是它 | 规划师提议 |
| `reworkOf` | 返工基于哪条意见（可选） | 规划师引用，系统核对 |
| `note` | 给席位的一句上下文，随派发一起出现 | 规划师提议 |

系统在真正派发前校验：阶段是否 active、席位角色与权限是否允许、并行数是否超过 `max_active_assignments`、预算是否到线、阶段依赖是否满足、验收席位独立性是否被破坏。校验失败时把原因回给规划师并写入时间线，**不静默改派**。提案里的自查方式只给席位做自检用，不等于阶段验收命令；阶段是否通过仍以 `stage.acceptance` 与证据为准。

**七条硬规则**

1. 只有系统能唤醒席位；规划师产出的是提案，不是直接发给其他 agent 的消息。
2. 派发只能落在当前 active 阶段，不能预派后续阶段，不能改阶段门禁或验收命令。
3. 被拒绝的提案必须带原因回到群里；规划师可以重提，但不能绕过校验。
4. worker 的回报进房间记录，不回给规划师私聊；汇总仍由阶段门禁和证据完成。
5. `@` 只是显示层，不构成权限；写在提示词里的“转给某某”不会产生派发。
6. 人可以直接接管：暂停、停止、返工、改验收命令仍按现有路径生效，派发不能绕开。
7. 全链路可审计：提案、校验结果、实际派发、worker 回报都进 transcript；调度台仍然只建议，不因此获得跨房间自动路由。

**编排策略（v1 已落 2026-11-12）。**

| 策略 | 派发形状 | 适用 | 边界 |
|---|---|---|---|
| `pipeline` 流水线 | 每阶段一个执行席位；优先用规划师提案里的 `assignees`，没有就用第一个执行席位 | 默认 | — |
| `parallel` 并行扇出 | 提案里的执行席位同时开工（默认全部），系统合并候选后统一验收 | 互不重叠的改动 | 少于两个执行席位时显式降级并写入系统消息 |
| `critique` 对抗复核 | 派发仍是单席位；验收席位收到“先找反例、边界输入和最可能失败路径”的复核要求 | 关键交付 | 不改验收命令，不增加席位，也不替代人签字 |

策略注册在 `server/crew/orchestration/`，与房型策略分开：房型决定阶段形状，编排决定阶段内怎么派活。房间记录 `orchestration`；开工卡可给出 `orchestration` 与每阶段 `assignees`，系统映射到真实执行席位并丢弃验收席位或未知席位。规划师提案只决定“谁做什么”，验收席位仍由系统按独立性规则派发。

**节奏与边界。** 首版保持“阶段开始派一次活”的固定路径；允许多轮自主改派是 opt-in，必须可撤销、可审计、默认关闭。派活是群内阶段协议的一部分，不是新的房型，也不是第二个权力中心。当前已落“开工卡提案 → 业务校验 → 系统派发 → 可见 @ 链路”，`best-of-N` 竞标与 `escalation` 升级链仍未接；界面还没有编排策略选择器，策略来自开工卡或 API。验收席位不由规划师挑选。

### 9.9 房间聊天：基座原生群聊，聊天与派活分离（2026-11-12）

**链路照搬 OpenMausBot**：一个房间有一个所有席位都在的基座群聊线程（`room.chatRoom`），输入框只往这个群发消息；每个席位在自己的群会话里说话，@ 只是点名，聊天回合不产出证据、不跑验收。真正的执行仍走阶段派发（§9.8），结果回到房间。

- **会话与工作分开**：聊天用共享群线程；执行仍用每个席位独立的工作线程与 worktree。聊天里的 @ 不会唤醒工作线程，只有阶段派发会。
- **自动选人**：群聊 `defaultResponder` 用基座 `auto`，由 decider 决定谁回答；decider 不可用时回落到规划师。Lodge 不写关键词路由。
- **上下文与沉默由基座负责**：群聊的窗口/增量、pass、room hold、post budget、同名 @ 处理都复用基座实现，Lodge 不再自造聊天意图分类或回合标记。hold 状态投影到高级面板。
- **最小提示**：群公告只写“这是对话；@ 点名；执行由派发完成”，不把阶段规则塞进聊天提示。身份与能力仍由各席位自己的 soul 提供。
- **聊天不执行工具**：聊天里的权限卡一律拒绝，并写一条系统说明；聊天不会读文件、改文件或跑验收命令。基座没有“同一席位按房间禁用工具”的装配能力，这是运行期能收到的最严边界；真正的装配期物理隔离需要独立聊天席位或基座支持。
- **记录边界**：聊天消息只进房间 `transcript`/消息流；证据、verdict、阶段状态只由工作线程和阶段门禁写入。
- **成员同步**：建房时创建群成员；建后加/移除席位会同步基座群成员，失败写系统消息。
- **未读**：基座群的 `unread` 投影到 `room.chatUnread`；侧栏显示蓝点，打开房间即标记已读（暂停时也可读）。
- **重连与旧房**：旧房间首次 attach 时补建共享群聊；已有聊天群会补成自动选人；建不出来就明确报错，不回退到“每个席位单独转发”的自造链路。
- **验收**：基座群里对执行者说“20 个字告诉我你能干啥”，执行者只回答、无工具调用、无 evidence/acceptance；这是判定链路正确的基准。
- **可重跑评测**：`npm run eval:chat` 复用房间席位 bot 建临时群，问一句，断言有回答且无工具活动，结束删除临时群；需要基座与 Lodge 在运行。

边界：`@所有人` 是产品文案，发给基座前映射成基座原生的 `@everyone`，不自己展开成员。来源标记、旧房聊天历史补写、post budget UI 仍未接（基座 WireGroup 没暴露预算字段）。

## 10. 协议与架构

### 10.0 基座与技术栈（已定）

> **这是目标态，不是当前接线**：当前 P0 是独立 `Lodge server` + 独立基座仓库 `crew-chat-base`（HTTP 8799），Windows/Linux Electron、runtime Assignment、上游 `message-db`/`thread-events`/`sse-fanout` 都未接入；macOS Electron 壳已接（ad-hoc zip）。当前事实以 `reuse-map.md` §8.5 为准。

| 层 | 选择 | 说明 |
|---|---|---|
| 外壳 | **Electron 43** | Mac arm64 先行，不发 universal；复用 OpenMausBot 的窗口与打包结构；当前 ad-hoc 签名，不接自动更新 |
| UI | **React 19 + Vite 8** | 当前 Lodge UI；不用 Tailwind，`createElement` 写法不改成 TSX |
| 运行时 | **OpenMausBot `server/runtime`** | Assignment 生命周期与不变量一行不改 |
| 引擎 | **OpenMausBot drivers + ACP** | 首版原生 Claude Code；第二厂商在 M4 接 Codex 或 ACP |
| 存储 | **`node:sqlite` WAL + 事件重放 + SSE** | 复用 `message-db` / `thread-events` / `sse-fanout` |
| 系统 | **macOS Apple Silicon，Node ≥22.5（推荐 24）** | `node:sqlite` 在 22 上可用但会提示 experimental；CLI 路径按 `/opt/homebrew/bin` 探测 |
| 不做 | LangGraph / CrewAI / AutoGen、自写 spawn 层、云 VM | 多一层状态机就会多一份真相 |

**为什么这个引擎层决定我们能走多远**

- **加引擎不改架构**：新引擎要么是一个 driver + 一行注册，要么是一条 `customAcp` 配置；核心 runtime、权限、UI 都不动。OpenMausBot 已覆盖原生 Claude / Codex 与 Gemini、Kimi、Cursor、OpenCode、Qwen、Cline、Copilot 等 ACP 引擎。
- **最容易烂的部分已经有人维护**：安装、版本探测、更新、握手、登录失效恢复、限额，这些是 CLI 集成里腐烂最快的地方；复用上游比自己写更稳。
- **产品层与引擎层解耦**：产品差异全部集中在 `server/crew/` 与 `ui/`；上游升级 driver 时，不需要重写房间、阶段、证据。
- **首版只接一个，是刻意的**：先证明“一条真实链路能跑通”，再在 M4 打开跨厂商独立性。首版就接两个引擎，会把失败原因混在一起。

**三个已定的产品口径**

1. **席位对外叫规划师 / 执行者 / 验收员**，内部仍是 planner / executor / verifier。技术名词不出现在主界面。
2. **完成态是交付单，不是聊天记录**（已落）：目标、通过阶段、每条命令与退出码、改动文件、commit；聊天退到下方。
3. **没有真实机制就不给控件**：主动档位、私聊入口、模板录制都等对应机制跑通再出现，首版不做假开关。

### 10.1 进程边界

> **目标态**：下图包含 Assignment Runtime 与 Approval Bridge；当前 P0 用基座群消息/回合和已接的工具审批桥，Assignment 未接。

```
UI ──HTTP+SSE(127.0.0.1, per-launch token)── Lodge server
                                               ├─ server/crew（自写产品层）
                                               │    Room Repo · Stages · Evidence · Seats
                                               ├─ Room Scheduler / Goal Runtime
                                               ├─ Context Builder（水位线）
                                               ├─ Approval Bridge（独立守门）
                                               ├─ Assignment Runtime（OpenMausBot，不改）
                                               ├─ Drivers / ACP（OpenMausBot）
                                               └─ SQLite（WAL）+ 事件重放
                                                     │ spawn
                                               claude -p --output-format stream-json --resume …
```

- 只有一个 runtime；UI 不持有计时器、不算 token、不推导状态
- 适配器返回 `Found / Missing / Unsupported / Denied / Failed`
- 不设单文件行数上限；约束是「一个文件一个变化原因，依赖只向内」，见 `设计思想.md` §9；单实例锁 + 数据目录锁

### 10.2 一个回合

```
1. scheduler 选出 member
2. 读 last_read_seq，取增量；过大则生成交接包
3. 拼 turn input：稳定 system + delta 消息 + 当前目标/阶段/任务（作为消息）
4. spawn CLI，流式解析；对外/变更类工具调用走审批桥
5. 结束：写 message(seq++)、更新游标、结算 token/cost
6. 有 evidence → 落盘；声明完成 → 触发 verifier
```

### 10.3 讨论串行，执行受控并行

- 普通发言按顺序
- 阶段本身串行：同一时刻只有一个 active 阶段
- 阶段本身串行；一个交付阶段里有多个执行席位时，各自 worktree 并行开工（`max_active_assignments` 配额尚未接入，现阶段多执行即全并行）
- `@` / 点名 → 在配额内同时开工，谁先好谁先发
- 要接着别人的结果做 → 接力
- 批次落地后只唤醒派活的人一次
- **讨论阶段全员只读同一份 base**

### 10.4 工作区隔离

- 讨论阶段：planner 在自己的只读克隆里；写工具经审批桥拒绝（exec 仍不是文件系统沙箱）
- 执行阶段：每个 executor 在自己的 git worktree；多个执行席位同阶段并行，候选分支合并进房间 integration worktree 后再验收
- 验收阶段：executor 先提交候选 commit；verifier 在一次性 detached worktree 副本里只读执行 acceptance；**verifier 不合并、不提交**，副本里的写入在下一次复核前丢弃
- 候选分支自动合并到房间 integration 分支；合入主分支由 lead 或人决定，**绝不自动 push**

> 单执行时 executor worktree 就是房间交付目录；多执行时另建 integration worktree 作为交付目录，候选分支先合并到这里。planner 克隆与 verifier 副本在外；源仓库主分支不动。人签字后再提交 `.crew` 结论。

**生命周期（已落）**：创建时为 worker/verifier/integration 复制 `.env`/`.env.local`、软链 `node_modules`，并分配执行/验收/集成端口；端口写进工作提示词与验收命令的 `PORT`。候选 commit 与验收 diff 排除 `.env`/`.env.local`/`node_modules`/`.crew`。**验收命令在一次性 detached worktree 副本里执行**：先落候选 commit，再在副本跑命令；diff 在提交前采集，副本不写回交付 worktree。网络默认 deny：macOS 用 `sandbox-exec`，Linux 用 `unshare -n`；Windows 用 WSL2 里的 bubblewrap（`--unshare-net` 断网，根只读、仅当前副本与 `/tmp` 可写），`CREW_ACCEPTANCE_NETWORK=allow` 显式放行。Windows 没有 WSL2 或 bubblewrap 时 fail closed；适配器有注入式单测，尚未在 Windows 真机实跑。房间完成/停止后清理非交付席位工作区，保留交付仓库与候选分支；启动与每 6 小时 GC 已知房间；未知孤儿目录默认不删，`CREW_WORKTREE_GC_ORPHANS=1` 才按 TTL（默认 7 天）清理；创建前检查磁盘水位（`CREW_DISK_MIN_FREE_MB`，默认 512MB）。**边界**：`node_modules` 是共享软链，不适合在工作区里改依赖；一次性副本只隔离交付目录写入；macOS/Linux 的网络隔离不限制文件写入，Windows 的 WSL 适配器才有 cwd 写边界；Python venv、本地数据库与端口强制隔离尚未做。
>
> 这一条是对 Grok Bot "所有 Bot 共用一台云电脑"的直接反选。

### 10.4.1 Workspace 端口：git 是默认实现，不是本体（设计裁定 2026-11-12）

**裁定**：房间记录、目标、证据、交接包都不依赖版本控制；版本控制、隔离、候选、合并与 diff 是 Workspace 端口的能力。git 是默认 provider，不是唯一 provider。

**端口**：业务层（建房、回合、完成）只依赖 `workspace.js` 暴露的 provider，不直接调用 git。provider 暴露 `capabilities()` 与七个动作：

| 动作 | 语义 | git provider | direct（普通目录默认） | plain（显式复制） |
|---|---|---|---|---|
| `probeSource({ source })` | 判断源目录能否开房 | 必须在 git work tree 内 | 目录存在且可读 | 目录存在且可读 |
| `prepareRoom({ source, short, seats })` | 准备工作区 | worktree / clone / 分支 | 原地使用源目录，不复制 | 复制目录，分配端口 |
| `changes({ path })` / `rangeChanges({ path, base })` | 变更证据 | 补丁 diff | 文件清单 + 哈希 | 文件清单 + 哈希 |
| `submit({ path, turnId, name })` | 候选 | candidate commit | 无 | 无 |
| `integrate({ path, branch })` | 并行汇总 | merge 分支 | 不支持并行 | 按文件复制，同路径不同哈希记为冲突 |
| `isolatedCopy({ source, ref })` / `removeIsolatedCopy` | 一次性验收副本 | detached worktree | 临时复制目录 | 临时复制目录 |
| `persistRoom({ room, files })` | 完成留痕 | 本地 commit 一次 | 房间记录已落盘，无 commit | 房间记录已落盘，无 commit |

另有 `pruneSeats(room)`、`cleanupRoom({ source, workspaces })`、`head({ path })`、`refreshReviewCopy(...)`、`scratchRoot()`，用于生命周期与复核。

**房间根与版本控制解耦**：`roomRootOf(room)` 是记录落点；`repoPath` 字段暂保留为兼容名，不改已存房间与交接包。`room.workspace = { provider, capabilities }` 记录实际 provider；旧房间没有该字段时按 `git` 解释。

**能力降级**：
- 命令 + 退出码仍是验收主证据，不因 provider 改变。
- 无 git 时 evidence 记 `vcs:'none'`，变更是文件清单而不是 patch；UI 写“文件清单”，不写“diff”。
- 无 commit 时完成态留痕是房间记录 + 交接包，不写“本地 commit 一次”。
- 无 merge 时多执行只能顺序执行，或按文件复制并在同路径冲突时停下；不宣称分支隔离。
- 门禁与 UI 只读 `room.workspace.capabilities`，不猜 provider。

**迁移顺序**：
1. 语义收敛：`roomRootOf` 与 `repoPath` 兼容；文档分离“房间根”与“版本控制”。
2. 抽端口、行为不变：git 调用收进 `workspace-git.js`；建房、回合、完成链路依赖 provider；测试全绿。
3. 能力入库：房间写 `workspace` 与 capabilities，evidence 带 `vcs`，完成文案按能力分支。
4. direct / plain provider：非 git 目录默认 direct 原地修改；只有显式 `workspaceProvider: 'plain'` 才复制隔离。
5. 交接包联动：非 git 房间完成时，交接包就是归档。
6. 门禁：除 `workspace-git.js` 外，`server/crew` 不直接调用 git；文档写清 git / direct / plain 三种 provider 的差异。

**当前（2026-11-12）**：第 1–6 步已落。`workspace.js` 是端口注册表，`workspace-git.js`、`workspace-direct.js` 与 `workspace-plain.js` 是三种实现；`room-create.js`、`live-turns.js`、`service.js`、`workspace-gc.js`、`roster-recommend.js` 只通过 provider 调用；建房写入 `room.workspace = { provider, capabilities }`；`boundary.test.js` 要求除 `workspace-git.js`（以及 `paths.js` 的默认根探测）外不得直接调用 git。能力已用于：evidence 带 `vcs`；完成留痕按 `commit` / `git-unavailable` / `archive` 分支；并行执行在没有 `merge` 能力时建房即拒绝；一次性副本与候选提交按能力跳过；UI 显示工作区能力与「无 VCS」，变更证据按 `vcs` 标成 diff 或文件清单。direct provider 是普通目录默认：原地修改、文件清单证据、无 commit，用户选中的目录就是工作区；plain provider 仅在显式选择时复制隔离，支持复制合并但合并冲突要人工处理。边界：direct 只支持一个执行席位；plain 复制合并不传播删除；本机 git 不可用时仍按 git provider 能力降级。

### 10.5 引擎适配器

```ts
// P0 实际端口：房间级语义；start/resume 流式事件端口是后续目标
interface Engine {
  rooms(): Promise<Room[]>
  history(sessionRef: string): Promise<{ messages: Message[] }>
  sendTurn(input: { roomId: string; text: string }): Promise<{ accepted: boolean; messageId: string | null }>
  cancelTurn(input: { roomId: string }): Promise<{ cancelled: boolean; reason?: string }>
  usage(roomId: string): Promise<{ turns: number; costMicroUsd: number }>
  capabilities(): { resume; streaming; approvals; structuredOutput; subagents; cancel; provisioning; mentions; mcp; skills; schedules }
  instances(): Promise<Array<{ id; engine; name; available; models; capabilities }>>
  health(): Promise<{ ok: boolean; error?: string }>
  createSeatBot(input: { name; soul; description; approval; mcp; engine? }): Promise<SeatRef>
  createRoom(input: { name; goal; bulletin; members; cwd; leadId }): Promise<{ id: string; sessionRef: string }>
  deleteSeatBot(botId: string): Promise<void>
  deleteRoom(roomId: string): Promise<void>
  subscribe(input: { roomId; sessionRef; onEvent; onState }): () => void
}
```

`createSeatBot` 的 `engine` 是席位声明的引擎类别（如 `claude-cli` / `codex-cli`）；Engine 适配层通过基座 `/api/instances` 绑定到可用 instance/model。不可用时显式回退默认引擎，写「引擎降级」消息，不静默伪装成请求的引擎。`/api/state` 暴露只读 `engines`（available、原因、默认模型、capabilities），Advanced 显示可用引擎与降级原因；不做引擎选择器。当前机器只有 Claude 可用，Codex/Grok 会回退；能力矩阵参与策略仍未接。

`Event` 的 `text_delta / tool_call / permission_request / usage / done` 仍是后续流式端口的目标；P0 由基座消息、activity 与 digest 归一化。`Room` 只暴露 `id/name/sessionRef/goal/working/busyRef/cwd/usage`；`group/thread/bot/defaultResponder` 不进入 crew。

这是**产品层依赖的端口**，不是要重写引擎注册表：OpenMausBot 的 `server/drivers/` 已实现等价能力（原生 Claude/Codex、ACP、重试、限额）。P0 不接 runtime Assignment，使用基座群消息与回合；Assignment 是后续目标。新增引擎仍然只动 driver 或 `customAcp`。`boundary.test.js` 会拦住 crew 里的基座词汇与跨层 import。

**登录态**：用 CLI 自己的登录，不传 API key；子进程 env 剥离其他 provider 的 key。

**对外动作先审**：发消息、push、删文件、装依赖，一律进审批桥。审批桥是独立判定，不与被审对象共享上下文（Muse 的 Sentinel 思路）。**当前已接人工审批桥 + 规则守门 + 异步独立模型守门**：外部命令命中后挂起基座权限卡，`gate.js` 只看命令语义、席位角色与房间约束，给出允许/需判断/拒绝建议；`gate-agent.js` 再异步创建一个临时独立席位线程，只看事实并返回 JSON 建议，用完即删。两者都不改变“人最终决定”；独立复核会话已落（每席位独立基座线程 + 盲审包），稳定跨厂商仍依赖第二可用引擎。

## 11. 数据模型（最小集）

先裁定权威性，否则表怎么建都会打架：

| 对象 | 权威 | 规则 |
|---|---|---|
| 运行时状态（阶段、任务、游标、审批） | **SQLite** | 唯一写入者；状态变更与 `events` 在同一事务里提交 |
| 消息与事件日志 | **`transcript.jsonl`** | 先追加并 fsync，再提交 SQLite；启动时可从它重建索引 |
| `BRIEF.md` | **人** | runtime 只读；首次可生成初稿，之后按 mtime/hash 重读，绝不改写 |
| `GOAL.md` / `CONCLUSION.md` | **runtime 投影** | 可重写；不是编辑对象 |
| `decisions.md` | **人** | runtime 不写 |

三者冲突时：消息以 transcript 为准，运行时状态以 SQLite 为准，意图以人写的 BRIEF 为准。

**done / constraints 裁定（设计裁定，代码未接）**：`BRIEF.md` 是 title、objective、done、non-goals、constraints 的唯一权威；目标模型里的 `goals.done_json` / `non_goals_json` / `constraints_json`、`source_hash` 解析缓存与 `revise` 流程尚未实现。当前 P0 仍用房间 JSON + BRIEF，没有 `goals` 表或 `revise` 路由；实现时 `revise` 先写 `BRIEF.md`，再重建缓存，runtime 不直接改写 BRIEF。

> **当前 P0 原型**：SQLite 使用 `room(id, payload, version)` / `messages(seq, id, room_id, payload)` / `room_event(seq, ...)`；`seq` 是全局事件游标，不是按房间/分支。下面是目标关系模型；迁移只改 `store.js`，旧 payload 可读（`store.test.js`）。`events.jsonl` 是面向 clone/交接的 append-only 审计镜像，SQLite `room_event` 是查询索引；两者由同一次事件写入产生。

```sql
rooms(id, title, kind(room|dispatch), repo_path, strategy, template_id, independence(vendor|model|none),
      max_rounds, budget_micro_usd, last_seq, created_at)
members(id, room_id, name, handle, kind(human|bot), engine, model, station,
        write_scope, sort_order, speak_budget, is_verifier, last_read_seq)
messages(id, room_id, branch_id, seq, author_kind, author_id, kind(chat|pass|system),
         text, mentions_json, reply_to, created_at)
branches(id, room_id, parent_message_id, created_at)   -- 主线 branch_id = 'main'
turns(id, room_id, member_id, status, session_ref, last_read_seq,
      input_tokens, output_tokens, cost_micro_usd, started_at, ended_at)
goals(id, room_id, title, brief, state(drafting|active|paused|complete|stopped),
      objective, done_json, non_goals_json, constraints_json, source_hash, -- parsed cache of BRIEF.md
      current_stage_id, no_progress_wakes, idle, revision, created_at, updated_at, ended_at)
goal_stages(id, goal_id, idx, kind(deliverable|decision), title, acceptance_cmd,
            evidence_ref, state(pending|active|passed), verifier_id,
            reject_count, rework_feedback)
assignments(id, room_id, goal_stage_id, parent_id, assignee_id, title,
            state(queued|running|needs_input|waiting|resume|terminal), reject_count, evidence_id)
evidence(id, assignment_id, command, exit_code, output_ref, diff_ref)
approvals(id, room_id, turn_id, tool_call_id, action, state, decision, expires_at)
dispatch_requests(id, room_id, text, state(pending|suggested|confirmed|declined|closed),
                  suggestion_json, target_room_id, target_member_id, assignment_id, decided_at)
engine_capabilities(engine, version, resume, streaming, approvals, structured, subagents)
events(event_id TEXT PRIMARY KEY, room_id, branch_id, seq, type, payload_json, at)
```

- `(room_id, branch_id, seq)` 唯一；`seq` 由 `rooms.last_seq` 在事务里分配。fork 出 `branches`，每个分支有自己的 seq 域
- `members.last_read_seq` 是当前游标；`turns.last_read_seq` 只是回合开始时的快照
- `assignments.state` 由基座 runtime 写，产品层只读；`rework` 是事件，不是状态；验收失败回 `queued`，`reject_count++`
- 一次只有一个 active Goal；`past_goals` 是 `state=complete` 的查询视图，不是另一张表
- 目标岛（§9.7）只读上表列出的字段：`goals.title/state/idle/current_stage_id` + `goal_stages` 的 acceptance/reject_count/rework_feedback + `assignments` 的 assignee/state + `evidence`。岛上没有自己的存储，也没有第二份状态
- `goals.idle` 由连续两次 goal check 无进展置位；`revision` 每次目标变更 +1，客户端按它刷新，不轮询整张表
- `kind=human` 的成员 `engine/model` 为空，不参与轮次，不计发言配额
- `kind=decision` 的阶段 `acceptance_cmd` 为空，`evidence_ref` 指向决策记录；`deliverable` 阶段相反
- 成本用整数 micro-USD；未知模型标 `unknown`，**不按 0 算**
- `messages` 建 FTS5 虚表
- 长消息：热表只存前 2000 字符 + 全文引用
- `kind=dispatch` 的房间没有 `repo_path`，成员只有 `read` 权限的前台席位，不存在 worktree
- `dispatch_requests.state` 只有 `confirmed` 才生成 Assignment；`suggestion_json` 存候选与理由，便于事后审计
- 调度台的汇总**不是表**：每次从 `goals` / `goal_stages` / `assignments` / `evidence` 现算，避免第二份真相
- Workspace / Org / Roster 表在 M6 之后引入；M0–M5 只有 `rooms.repo_path`
- 外键、索引、迁移脚本留给 `engineering-spec.md`，这里只锁语义

## 13. 验证清单

1. 固定三人小队 + 你就"给本仓库加 `--verbose`"讨论 5 轮，产出 `plan.md` 与一次 commit
2. 中途 @ 另一个席位，它在下一回合插入且能看到此前全部发言
3. 连续 6 轮全员 pass → 暂停并标"等你说话"
4. Stop 后 500ms 内子进程消失，transcript 保留已产生部分
5. 编制里放两个执行席位后，两人同时改 `package.json`，worktree 独立，冲突在集成时可见
6. acceptance 失败 → 阶段标返工、任务回 `working`，附失败输出，注意力显示“验收未通过”
7. 无证据（或无命令）的 pass 被工具拒绝
8. 断网 → 回合标 `uncertain`，恢复后**不自动重发**
9. 审批卡 10 分钟无人答 → 暂停 + 标"等你"，**不标 deny**
10. 重启后，已产生外部动作的回合不重跑
11. 配置了第二厂商时，producer 是 claude，verifier 不能也是 claude
12. 从第 3 轮 fork，两条支线互不影响，可并排对比
13. 对齐只提出 ≤3 个带推荐答案的问题，人可一句"按你说的"通过
14. 连续两次 goal check 无进展 → `waiting_on_user`
15. `revise` 后已通过的阶段保留
16. 从打开到第一次输出 ≤60 秒，全程不改任何设置
17. 任何时刻界面上最多一个待你回答的问题
18. 关掉再打开，进度与最后状态一致（不丢、不重跑）
19. 两个成员私聊后，主时间线只出现一条结论，不出现私聊全文
20. 评审类议题的第一轮不包含其他人的发言（日志可证）
21. verifier 收到的 diff 不含作者与引擎信息
22. 导入模板后权限正确：Planner 无写、Executor 只写自己 worktree、Verifier 可跑命令但无写
23. 只有一台 CLI 时，验收卡显示"独立性降级"，不冒充跨厂商
24. 人在群里补一条约束，任务继续，已通过阶段不重跑
25. `decision` 阶段没有 `acceptance_cmd` 也能推进，但必须有人点过；`deliverable` 阶段没有命令则无法 active
26. 一句"我不知道该找谁"落进调度台成为请求；给出建议后，你点确认之前目标群没有任何新 Assignment 或消息（日志可证）
27. 调度台没有 `repo_path`，任何改文件 / 跑命令的动作被工具拒绝
28. 摘要里每条结论都能点回具体群 + 阶段 + 证据；无法映射到投影的结论不出现在摘要里
29. 调度台只能引用目标群 Verifier 的 PASS，不能自己产出 PASS，也不能改任何群的 `done`
30. 界面上的每句"已写入 / 已提交 / 不同厂商"都能在房间仓库的 `.crew/rooms/<id>/` 或房间引擎配置里找到对应事实；找不到就不显示这句话
31. 样例与模拟数据在证据卡、验收卡上明确标注，不被当成真实执行
32. 建队时选圆桌/存档生成的阶段是决策型；只有一台 CLI 时席位引擎一致，验收卡标"独立性降级"
33. 新建房间的交付阶段要么有真实引擎可跑，要么有明确标注的模拟步骤；界面不出现无路可走的状态
34. 完成后的结论 commit 包含 `.crew/rooms/<id>/` 的 BRIEF/GOAL/CONCLUSION/transcript/events/evidence；只靠该 commit 能读到当时的目标、done、证据与结论，不依赖原席位会话
35. `npm run eval:planning` 对 3 个黄金房间给出通过/失败与原始开工卡；改规划师提示词或换引擎后能重放对比，不拿单次最好成绩当结论
36. 真实房间中 planner/verifier 请求 Write/Edit 时被审批桥拒绝并留下「权限拒绝」消息，文件未被创建；exec 仍可跑验收命令，但不把「exec 可写临时副本」说成文件系统硬隔离
37. 验收命令在一次性副本执行：命令写出的 side-effect 不出现在交付 worktree；候选 commit 先落盘，evidence 只记录交付改动，并带 `isolated: true`、`sandbox` 与副本路径。网络默认 deny；没有平台适配器时 fail closed

### 15.3 私密 dogfood（M3 后，当前下一步）

“M3 已过，仍不公开演示”不等于“不接触用户”。下一步找 5–10 个长期维护同一仓库、需要交接或追责的种子用户，做私密 dogfood；只收卡住点，不做宣传。

**第二阶段（已落 2026-11-12）**

- **目标任务模型（已落）**：阶段任务状态机（pending/working/reported/done/failed）、任务级负责人与证据引用；房间 revision 暴露在高级面板；完成时归档 `pastGoals` 并在高级显示历史目标；目标岛显示任务行。未做：revision 冲突重试/并发合并（当前本地单人）、任务依赖 DAG、历史目标下钻页。
- **用量趋势（已落）**：`/api/usage` 支持 24h/7d/30d/12w/12m，按小时/天/周/月分桶；界面只保留调度台最近 7 天 Token 柱状趋势，独立用量页、花费/缓存命中/回合/房间排名均不展示。未做：按模型/席位的用量拆分（账本目前到房间级）、导出。

**借鉴边界**：目标/任务模型与 Token 趋势参考 Claude-Bot；`AGENTS.md/CLAUDE.md` 发现与 MCP 超时/取消参考 OpenMausBot。Lodge 的真相仍是房间记录 + BRIEF + 证据，不引入他们的宿主状态或云端多人记忆。

### 15.5 房间能力与子房间（opt-in，接口预留）

**裁定（2026-11-12）**：不引入“调度房 / 圆桌房 / 流水线房 / 基线房”五个并列房型。底层仍是一个 Room；需要编排时只开一个能力 `dispatch`。圆桌是讨论阶段与席位行为，流水线是阶段依赖，基线是版本能力，执行房是默认房间。五个名词不进入首屏，也不做房型选择器。

**数据接口（已预留投影字段；路由、存储写入和 UI 未接）**

- `room.capabilities.dispatch: boolean`，默认 `false`。
- `room.parentRoomId: string | null`，默认 `null`。
- `room.childRoomIds: string[]`，默认 `[]`。
- `presentRoom` 已暴露这三个只读投影字段；旧房间自动得到 `{ dispatch: false } / null / []`，不改旧 payload。
- 未来创建子房间：`POST /api/rooms/:id/children`，父房间必须 `dispatch=true`；子房间是普通 Room，独立目标、席位、工作区、预算和签字。
- 未来读取子房间：`GET /api/rooms/:id/children`，只读返回状态、阶段、`needsYou` 与交付摘要。
- 未来回传结果：`POST /api/rooms/:id/children/:childId/attach`，把子房间交付摘要作为父房间证据/消息，必须人确认；不做自动汇总、自动派活。
- 未来开关能力：`POST /api/rooms/:id/capabilities`，只在高级里开关 `dispatch`；已有子房间时拒绝关闭。

**约束**

- 最多两层：根房间 → 子房间；子房间不能再有 children。要更深时重新评估，不默认放开。
- 每个父房间最多 4 个子房间；子房间必须有自己的目标、验收和人的签字。
- 父子各自独立预算、工作区、证据；父房间不写子房间仓库，也不替子房间签字。
- 不自动路由、不自动执行；子房间结果只能只读展示，或由人 attach 成父房间证据。
- 首屏不出现房型；只在高级里出现“允许拆子房间 / 拆成子房间”。
- 旧房间不迁移、不自动开 `dispatch`；存储只加可选字段，结构变化时 `version` 递增。

**为什么不做五种房型**

| 提法 | 落点 |
|---|---|
| 执行房 | 默认房间，不需要类型名 |
| 流水线房 | `stages.dependsOn` 串行，不是新实体 |
| 圆桌房 | 讨论型阶段 + 席位发言行为 |
| 调度房 | 有子房间的普通房间，`dispatch` 能力 |
| 基线 / Git 房 | 版本快照能力，放高级；普通用户不出现 Git 名词 |

**落地顺序**：先完成单房间 dogfood；真实用户重复卡在“一个房间装不下”2–3 次后，再做 opt-in 子房间。当前只留投影字段与文档契约，不实现路由和 UI。

### 15.6 房型策略（2026-11-12 已落）

房型不是核心里的 `if`，而是 `server/crew/room-types/` 下的策略注册表。核心只做 `resolveRoomType(body.roomType)`，调用策略的 `normalize / buildStages / autoStart`；新加房型不改 `room-create`。

| 策略 | 对外名 | 默认席位数 | 阶段 | 验收 |
|---|---|---|---|---|
| `task` | 任务房 | 由模板/人决定 | 对齐 → 交付 → 验收与结论 | 命令或人工 |
| `roundtable` | 圆桌派队 | 主持 + 2 位讨论者 | 圆桌讨论 → 结论 | 人工 |
| `archive` | 存档房 | 1 位档案 | 存档与交接 | 人工 |

- 未知 `roomType` fail closed，不静默回落。
- 旧房间没有 `roomType` 时按 `task` 解释；`/api/state` 暴露 `roomTypes` 供 UI 使用。
- UI 首屏只放目标、工作空间、房型、项目约束、本地模板；默认任务房；非任务房不跑验收命令，直接由人确认结论。手动选人入口不做，编制由 Lodge 出方案。
- 五种房型仍不进入首屏；流水线、基线、调度分别落在阶段依赖、版本能力和子房间 opt-in，不新增实体。
