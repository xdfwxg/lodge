# 验收重设计计划：交付自带证明

> 这是一份执行计划，不是产品承诺；完成后再把稳定下来的规则写回 `Lodge.md` 和 `docs/architecture.md`。

## 目标

让“完成”从验收员的文字判断变成可重跑的证据，同时不把证明做成用户要读的报告。

三层目标：

1. **契约 ≈ 真实目标**：规划师把可观察结果、边界、非目标和假设写清并冻结。
2. **产出 ≈ 契约**：交付自带可重跑的 `verify`，平台执行，验收员找反例。
3. **人只使用成果**：成功时验收不可见，失败时只出现一条可复现的失败。

仍然不承诺 100% 命中意图；目标是“大概率符合、错了能看见、看见能退回”。

## 设计

### 1. 契约是一等对象

- 规划师产出房间级契约：3–6 条可观察结果（id + 一句“看到什么算做到”）、边界、非目标、关键假设。
- 平台校验形状后冻结；阶段交付物引用契约 id。
- 规划师仍只定义“做到什么算完成”，不定义验收方法。
- 契约只保留一份，阶段、验收、交付卡都引用它。

### 2. 交付自带 proof 和 verify

- 每个可判定阶段的交付包含：
  - `verify` 入口：一条命令或一段可重放流程。
  - 条款映射：每条契约 id 对应一条证明步骤和预期输出。
  - 证明产物：命令输出、截图、数据对比、产物摘要。
- 平台在干净副本里执行 `verify`，记录输出和产物摘要，绑定到证据 id。
- 证明跟着成果走：下一轮、CI、外部审计都能重跑同一条入口。
- 没有 proof 或 proof 跑不绿的条款，直接标“未证明”。

### 3. 验收员只负责攻击

- 开工前，验收员针对契约写攻击计划：边界输入、异常路径、真实用户流程、性能对比。
- 交付后，平台跑这些反例；找到反例就 REJECT，并附可重跑复现。
- 找不到反例才 PASS，并写清“尝试了什么、没有证伪”。
- 验收员可以增加检查，不能删弱执行方的 `verify`。
- 高风险步骤两位不同厂商验收员各自独立攻击，全部通过才收口。

### 4. 产品表面：成功安静，失败说话

- 成功：结果卡就是成品；旁边一行 `试过：npm test · 2 个用例通过`，点一下重放。没有交付卡、证明卡、覆盖表、验收意见。
- 失败：一行说清哪条契约没做到，附一条可重放的复现和谁在修。
- 证明是给系统跑和审计用的，不是给人读的；主路径只显示结果。
- 证明和验收记录进“详情”和审计，默认收起；高风险或合规房间强制展开。
- 主界面只出现：目标、进度、结果、失败、修；不出现“验收、覆盖、证据、反例、通过”。
- 岛只说「已交付」；结果卡是成品，不是报告。

### 5. 主观工作不假装可验证

- 阶段分两类：`可判定` 和 `需判断`。
- 可判定阶段走 proof + 反例 + PASS。
- 需判断阶段只核对硬约束，交付明确标成草稿，由人判断；不计入 PASS。
- 高风险可判定阶段双厂商；需判断阶段不硬塞第二位验收员。

### 6. 测量

- 验收探针在交付后注入缺陷，测验收员会不会真的跑出反例；记录抓出、误放、误拒。
- 规划探针测契约有没有漏掉隐藏假设。
- 真实房间记录：从目标到第一版的时间、人的否决率、返工次数、成本。

## 首个落地切片

只选一种可判定成品（例如网页预览，或一条能跑的命令输出）和一个房型，端到端做通：目标 → 契约 → 交付 proof → 平台跑绿 → 验收员攻击 → 结果卡重放。不要同时做代码、文档、设计三种成品；先量“从目标到第一版”的时间，再决定扩不扩。

## 分阶段

### 阶段 0：已完成的地基

- 覆盖表、亲手验过的工具痕迹、验收员池、高风险双厂商。
- 写文件提到 `npm install` 不再误弹安装审批。
- `@` 交接行与聊天正文对齐。
- 交付后注入缺陷的探针改造已实现，正在验证。

### 阶段 1：契约与 proof 对象

- 新增共享契约：`contract`、`proof`、`verify` 的形状和校验。
- 规划师提示词和技能包加入契约字段；冻结后写进轮次。
- 新增平台 `verify` 执行器：干净副本、超时、资源限制、输出摘要。
- 阶段交付卡开始显示“未证明 / 已证明”，不改变现有验收判定。
- 测试：形状、注入越界、超时、失败输出、旧数据清理。
- 完成标准：一个可判定阶段能交 proof，平台跑出结果并绑定证据；没有 proof 不能 PASS。

### 阶段 2：验收员证伪

- 验收员开工前提交攻击计划；平台存为这一阶段的复核契约。
- 交付后平台执行攻击；REJECT 必须附可重跑复现。
- PASS 条件改为：proof 全绿 + 预算内没有反例 + 覆盖全部契约 id。
- 高风险双厂商各自攻击，全部通过。
- 测试：注入缺陷被抓、弱 proof 被拒、反例越界、预算耗尽、双验收。
- 完成标准：探针连续多轮能抓到注入缺陷；误放率有数据。

### 阶段 3：产品表面收敛

- 成功时隐藏验收/证明界面；失败只留一条复现。
- 结果卡变成成品入口；支持重放 `verify`。
- 删除主路径上的 verdict 卡、覆盖表、证明卡。
- 端到端：目标 → 成品 → 重放；失败路径只出现一条红线和复现。
- 高风险和合规房间强制展开“怎么验的”；普通房间默认收起。
- 完成标准：用户不需要读任何验收文字就能使用成果；失败时才需要看证据。

### 阶段 4：主观分型

- 阶段加 `checkable` / `judgment` 类型；建房和规划师提交时校验。
- 判断型交付明确标草稿；人收下或退回；不产生 PASS。
- 结果卡文案和状态分流。
- 完成标准：写作/设计房不再显示“验收通过”；人看稿即可。

### 阶段 5：测量与运营

- 夜间跑验收探针，写模型池；误放率高的模型不进池。
- 规划探针测契约质量。
- 记录真实房间的否决原因，沉淀成契约模板和反例库。
- 完成标准：每个验收模型有抓出/误放/误拒数据；池门槛可执行。

## 文件与模块

- `shared/contract.js`：契约形状、冻结、条款校验。
- `shared/proof.js`：proof/verify 形状、执行结果。
- `server/crew/rooms/studio/proof-runner.js`：干净副本执行、超时、产物摘要。
- `server/crew/rooms/studio/falsify.js`：攻击计划、反例执行、PASS 门禁。
- `server/crew/rooms/studio/review.js`：接入 proof 结果和反例。
- `server/crew/gate/mcp-server.js`：`submit_verdict` 增加 proof/falsify 引用。
- `ui/src/room/studio/result-card.js`：成果入口、重放、失败复现；成功隐藏验收。
- `evals/verifier-probe/`：交付后注入缺陷、按模型计分。
- `docs/architecture.md`、`Lodge.md`、`思想.md`：稳定后回写。

## 验证与门禁

- 单测：契约/proof/执行器/反例/门禁/注入越界/超时。
- UI 端到端：成果入口、重放、失败复现、主观草稿、窄屏暗色。
- `npm run check:done` 全绿。
- 真实探针：至少 10 个缺陷样本、5 个对照样本，误放率有数据。
- 验收矩阵补上 proof、反例、主观分型、模型池。

## 风险与对策

- **proof 写得弱**：验收员攻击 + 规划探针 + 高风险双验收；平台只证明“跑过”，不证明“证明得对”。
- **执行脚本不安全**：干净副本、只读源、超时/内存限制、外部动作审批；不默认联网。
- **成本与延迟**：只对可判定、多阶段、高风险任务启用；单步小任务保留轻量路径。
- **主观工作假保证**：不产生 PASS，明确草稿。
- **旧数据不兼容**：直接清掉，不做兼容层。
- **人仍然不看**：成功时不给报告；失败时只给一条复现，降低判断成本。

## 非目标

- 不新增第四种底层角色。
- 不把验收方法交回规划师。
- 不做多 AI 辩论界面。
- 不承诺 100% 命中目标。
- 不给主观工作伪造可执行证明。

## 完成标准

一个可判定房间能走完：目标 → 冻结契约 → 交付 proof → 平台跑绿 → 验收员攻击无果 → 人直接使用成果。失败时，人只看到一条可复现的失败。探针能证明验收员会抓到注入缺陷；主界面不再用验收术语。
